# Decisions

A short, dated log of choices a future maintainer or agent might otherwise undo.
Add one line per decision: `Dn (YYYY-MM-DD): decision — why.` Replace a line
when a decision changes; git keeps the history.

- D1 (2026-10-13): Release with the Lupinum OSS `library-monorepo` workflow (Changesets, npm trusted publishing, protected `npm` environment) — every Lupinum repository shares one release, security and CI setup.
- D2 (2026-10-13): `@lupinum/ginko` declares no peer dependency on `@lupinum/ginko-content` — `ginko-content` depends on `ginko`, and a cycle between published packages stops `scripts/release.mjs` from packing. `ginko` still loads `ginko-content` with a dynamic import and tells users to install it; it is only a devDependency (types, tests) and an unbuild external.
- D3 (2026-10-14): Every published package accepts Nuxt 4.6 and Nuxt 5: `nuxt` peer range and module `compatibility` are both `^4.6.0 || ^5.0.0-0` — a site can upgrade Nuxt without upgrading Ginko, and npm installs Ginko next to a Nuxt 5 prerelease without a peer conflict. Proof: `pnpm check:pack --nuxt5` (CI job `nuxt5`) builds every starter and the docs site from the tarballs on the Nuxt 5 nightly that `packages/ginko-i18n/browser/apps/n5` pins. Move that pin forward when a newer nightly is needed; drop the `-0` when Nuxt 5 is released.
- D4 (2026-10-14): Ginko writes all SEO output itself and needs no Nuxt SEO module; the one module every starter gets is `nuxt-og-image` (Takumi), because drawing images is not Ginko's job. With a Nuxt SEO module installed (listed, or through `@nuxtjs/seo`, and not `enabled: false`), Ginko leaves that output to it and hands it the site's data through Nuxt `moduleDependencies` defaults (order-independent; the site's own config wins) and per-request `site-config:init` hooks (language, preview hosts). `nuxt-ai-ready` is turned off while Ginko serves llms.txt — two producers of the same addresses. Share cards on a server need `NUXT_APP_SECRET` (nuxt-og-image signs their URLs); Ginko does not invent one, because Nuxt's sessions use the same secret: create-ginko writes one into `.env` and the build warns without it. Proof: the `docs-seo` site in `pnpm check:pack` (sites/docs with `@nuxtjs/seo`), on Nuxt 4 and Nuxt 5. Code: packages/ginko/src/nuxt/nuxt-seo.ts.
- D5 (2026-10-15): An entry is a page only in the languages it is translated into: `untranslated` defaults to `'hide'` for collections with a `route` and to `'fallback'` without one (`untranslatedMode`), and only a *missing* required translation counts, never an outdated one, a slug or an image description — German text under an /en URL (with `lang="en"` and hreflang) is wrong, while a typo fix in German must not turn a live English page into a 404. Opt-in `'fallback'` on a routed collection lists the entry with a link to its main-language page and gives it no URL in that language. `urlsFor` gives the page URLs (bundle, sitemap, hreflang, publicness); `routeUrls` gives every locale's address for cache refresh and URL clash checks. Code: packages/ginko/src/core/resolve.ts.
- D6 (2026-10-15, Matthias): An outdated translation (its print is of an older main-language text) stays on the site as it is until someone translates it again or confirms it. The Studio marks and lists it. Only a *missing* translation falls back to the main language (`fallback`) or hides a routed entry (D5) — a German typo fix must not turn a live English text German, nor remove the English note on legal pages; the risk that an old fact stays is handled by showing "outdated" where people act (field badge, language-switch line, save message, and the site-wide list). An outdated translation of a text the main language removed entirely goes away with it. `ResolvedEntry` has `outdated: string[]` and `blocking: string[]` (the missing required leaves) instead of `untranslated: boolean`. Code: packages/ginko/src/core/resolve.ts `localized()`, server lib/translation.ts `leafStatus`.
- D7 (2026-10-15): Addendum to D5: a picture's descriptions belong to its file. A save with a new file keeps only the description sent with it (ginko-server lib/content.ts `mergeField`) — an old picture's English text can never describe a new one. On a foreign-language tab the Studio edits only the description.
- D8 (2026-10-15): Addendum to D5 and D6: retired fields never count as outdated translations — core gives retired projections a throwaway `outdated` list, as it does for `blocking`.
- D9 (2026-10-15): An entry's address in another language is made from its translated title while the entry has no page in that language. A save of the title in that language makes the slug there again: the first free one in the brick and language, not taken by a static page or another brick's route. Once the page is online in that language, its address stays. The main-language slug stays as it was at creation. The client never sends a slug (`errors.addressFixed`). Undoing a title save does not bring the old slug back (that language had no page then). A proposal works out the slug when it is applied.
- D10 (2026-10-15): The slug rule for a new entry (per locale from its own text of the `from` field, else the main locale's slug) has one source, core `slugBases`. `entries.create` makes the slugs unique, and the Studio's preview uses them as they are — so the preview shows the address the server will make.
- D11 (2026-10-15): Quick-task sheets edit every language (Opus, option A). A Deutsch/Englisch switch in the sheet; one Speichern stores all languages as whole values of the changed root fields, with no `locale`, so the server needs no change. Why: new dishes, notices and events got no English where they are made, a new event kept a German English address because slugs are fixed at creation, and staff with only a task grant had no way to add English. Consequences: the per-root `fieldRevs` check guards whole-value saves; "Meine behalten" and a restored local copy apply only the person's own languages over the newer state (`ownChangesOver`), so a translation someone else saved meanwhile stays; local copies store their `base`; a per-language form does not offer a copy with texts in another language. Rejected: option B (English fields only in create sheets) and C (a toast that links to Inhalte) — they leave edit-task texts German, and C cannot give a new event its English address; and narrowing a sheet save to `locale` when only one language changed — a second wire format that does not fix `keepMine` on its own.
- D12 (2026-10-15): One entry title on the server. History lines, proposals, search hits, file uses and the agent's labels use core `entryTitle` (through lib/list `titleOf`), the same as the Studio. A planned week is "Woche ab <date>" in the main language. Rows already stored keep the title written at save time.
- D13 (2026-10-15): One rule and one button for a missing translation: "Text auf {name} übernehmen" (text, longtext and Markdown; whole source with a fold) and the tab dot `entry.groupHasGaps` belong to the translation slice. The model slice's own "Gleich wie {name}" version was reverted (e4eae88a, reverted in 236a04c8) — one rule and one button remain.
- D14 (2026-10-15): A picture in a Markdown text stores its own description only when the person wrote one (`![]($file.x)` otherwise). The library's description applies when the site is built, in every language, so a later fix in Dateien reaches every use. A component's `alt` prop stays the component's own text (copied from the library when chosen). Old texts with copied descriptions are not migrated.
- D15 (2026-10-15): Picture captions: option (a). No Markdown title captions, and no change to `GinkoMarkdown` rendering; "Bildunterschrift" in the editor turns the picture into the site's figure block instead.
- D16 (2026-10-15): The editor toolbar decides what fits from its measured width (`ResizeObserver`), not from CSS container queries — the overflow menu is portalled out of any container, and `container-type` on the editor frame would apply layout containment, which places the docked phone bar (`position: fixed`) relative to the frame. The sizes used for the fit sit next to the code and must follow the button classes.
- D17 (2026-10-15): A link to an entry stores the entry's ID (`$<area>.<id>`), not its address, so a later change of the address keeps the link working. The links are unreadable in the Markdown source view; that is accepted. Every import (`ginko import`, `pnpm local:pull`, the Studio backup ZIP) rewrites these links with the new IDs in seed.ts `importRefs`, which also parses the changed texts again and carries the translation prints. Only links in link destinations and reference definitions are rewritten; `$page.` links and code stay as they are.
- D18 (2026-10-15): Staff may change entries they created (Matthias). An entry a staff member creates stores `createdBy`. lib/access.ts `authorize` lets that person change it (never remove it) with a create task of its brick that they still hold; every field is allowed, as when creating. A save goes through a held edit task that covers the changed fields (the widest first) and through the create task only when none does, so an edit task's `needsApproval` keeps applying to the fields it covers; the create task's `needsApproval` applies otherwise. Losing the create grant ends the right. There is no backfill: entries made before this, and all entries of owners and admins, have no creator. The agent door uses the same check: `taskFor` falls back to the create task for own entries, and create-only staff get `ginko_revert` and `ginko_translate`. Backups (`ginko export`) do not carry `createdBy`, because user ids do not move between deployments.
- D19 (2026-10-15): Every staff text that says whom to ask uses "die Person, die dich eingeladen hat" (Opus, option A). The invite mail names that person. A missing right is shown muted, never in error red.
- D20 (2026-10-15): People's names (Opus, option B). Each person has one display name in `userSettings.name`, which only that person sets (Meine Seiten, or the invite page). Everyone in a team sees it, staff included. Owners and admins also see emails: they see "Name (E-Mail)" wherever a member is named (history, conflicts, files, keys, review, the proposal digest mail). Staff see a colleague's name, or "Ein Mitglied" when there is none, and never an email; the address alone shows until a name is set. The reader always sees themselves as "Du" (Who `{ self: true }`). Why: a name is whatever the person typed; the address is the identity they verified. Deleting the account deletes the name with `userSettings`. No names for former members or for platform admins who are not members.
- D21 (2026-10-15): Backup in the Studio (Matthias: backup in the Studio; Opus: option A, the ZIP is built in the browser): the browser builds the ZIP with client-zip from the public query `backup.download` (owners and admins; the same `snapshotOf` as GET /export), so a Studio backup and `ginko export` share one format (`pathOf` and `defaultDir` from `@lupinum/ginko/internal`). It streams to disk in Chromium; other browsers hold up to 1 GB in memory. No server-side ZIP job.
- D22 (2026-10-15): `grantGroups(schema, grants)` in `@lupinum/ginko/internal` is the one way to read grants as rights by area: Team page, invite mail and invite page use it, so the three cannot disagree.
- D23 (2026-10-15): Proposal outcome (Opus): the author gets an email only on rejection — the reason, plus a link that reopens the proposal (`/s/{slug}?task=…&reopen=…`; for an assistant's proposal the link goes to Verlauf). No email when approvers reject their own agent's proposal. No email on approval.
- D24 (2026-10-15): A save that becomes a proposal replaces (withdraws) the author's older open save on the same entry only when both have the same task, the same door (ui/agent) and the same language, and the new one writes every root field of the older one (confirmed leaves count by their root). Otherwise both stay open. The withdrawn proposal gets `decidedBy` = author. Why: the sheet starts from the open proposal, so the new one includes it; two open proposals for the same fields made one of them stale when approved.
- D25 (2026-10-15): Sign-out with local unsaved input (N2b, option A): Abmelden asks first when this browser holds unsaved input of this person (`window.confirm`: "In diesem Browser sind noch ungespeicherte Änderungen. Beim Abmelden werden sie gelöscht. Trotzdem abmelden?"). OK signs out and deletes only this person's copies, so shared computers stay clean; Abbrechen keeps everything. No question when nothing is stored; only copies that would still be offered back count (less than 14 days old). A refused sign-out keeps the session and the copies and says "Abmelden hat nicht geklappt." A session that ended elsewhere (revoked, expired, other devices signed out) keeps the copies for the next sign-in. Konto löschen deletes them without asking. - D34 (2026-10-15): The `planned` brick rule (core, option A, Opus). `planned: { field, next, from }` on single and collection: from the date in `from`, `next` replaces `field`. `next` and `from` are optional and set together. - D35 (2026-10-15): Rules across fields (a plan set by halves, a week start) bind only what is written now. They are errors in create, and in patch when the save touches one of their fields. Stored data that breaks them gives warnings in release and restore. Why: a platform release re-validates every entry of a brick whose fields changed, labels included, so an old half plan or a stored Thursday week must not block a release.
- D36 (2026-10-15): The weekly task (the edit task that presets a date to `@workWeek`) always covers the current work week. The server refuses any other week through it (`errors.weeklyTaskThisWeek`), and a proposal from an earlier week goes stale on approval. - D37 (2026-10-15): An `@today` prefill keeps a stored date that has not passed (stored >= today). Why: reopening "Heute geschlossen" moved tomorrow's closure to today. This applies to every edit task with `@today` (`hours.closedToday`, industrie's `closedOn`, `menu.soldOut`). Week tokens (`@workWeek`, `@nextWorkWeek`) always give the task's week. The agent door resolves the prefill the same way.
- D38 (2026-10-15): Gastro availability (option A, slimmed): `menu.onMenu` (optional boolean, default true, inside "Gericht bearbeiten", no separate season task), `menu.soldOutOn` (optional date; quick task "Gericht heute aus", the first menu task, prefilled `@today`; it resets by itself the next day), `events.soldOut` (optional boolean; quick task "Veranstaltung ausgebucht"). A fully booked event shows "Ausgebucht" instead of the booking link; in JSON-LD its offer has availability `SoldOut` and no booking URL.

- D43 (2026-10-15): Templates infrastructure (ginko-internal specs/TEMPLATES.md T3, T10). `templates/*` are workspace members; root `overrides` link the fixed group to `workspace:*`, and `bumpVersionsWithWorkspaceProtocolOnly` keeps `changeset version` from rewriting a template's committed range (`^A.B.0` of the next release per `changeset status`). Inside the repository a template's scripts run from the root (`pnpm --filter <name> run …`): its own pnpm-workspace.yaml (allowBuilds, for users) makes pnpm treat its folder as a separate root. create-ginko without `--template` keeps the plain starter (`template/`), and `--preset` keeps `presets/`, until templates replace them. The platform-ready gate checks core `withoutFiles(site)`.
- D44 (2026-10-15): Basics live in core as the subpath `@lupinum/ginko/basics` (TEMPLATES.md T5): opt-in, so a site that never imports it carries none of it; builders for presets are in `/internal`. Basics adopt the stored names of bricks that already exist: posts/authors/changelog store the `@lupinum/ginko-docs` shape (ginko-docs builds its bricks from them through `labelsIn(…, 'en')`, a sha256 pin guards its schema), `site()` and `legal()` take agency's names and values (no country field). preset-gastro's hours, notices, events and gallery are thin wrappers over the basics that pin 0.4's labels, tasks and default week; the one stored addition is `status` on hours (D49) — 0.4 sites and the hosted fixtures must keep their data. Factories write `source` only when passed; `withoutFiles(config)` is the platform twin (also used by `pnpm templates test` gate 2).
- D45 (2026-10-15): `country` (ISO 3166) in the site config; `serializeSchema` stores the resolved calendar as `holidays` (explicit `calendar` wins, a function is `custom`, a country without a calendar is `none` with a `ginko check` warning) (T6) — server, Studio, mail and site must count the same holidays. The Nuxt module exposes `runtimeConfig.public.ginko.country` and `.holidays`; `useGinkoSeo` fills a missing JSON-LD `addressCountry` (and remote job applicants) from it, so `siteJsonLd`/`jobJsonLd` need no country. Basics rules use no calendar unless given; only the gastro wrappers keep Austria as their 0.4 default. A schema without `holidays` (released before `country`) gets an "unknown" hours line on a day where Austrian holidays and none disagree, rather than a wrong one.
- D46 (2026-10-15): Status lines (TEMPLATES.md §7.1): `status` is a union, one per brick — `{ next }`, `{ count: true }` (needs `visible: until`), `{ missing }`, `{ age }` on collections, `{ hours: true }` on a single; drafts collections show "drafts · scheduled" without one. Computed on the server with core `brickStatus` (`sites.today`, staff see only bricks they hold a task on and only their own drafts). Due: the week is stale, entries end within 7 days (today and the six days after it), entries miss the field, the next entry starts within 7 days with a required text empty in a site language, or today's hours are unknown. The hours line runs basics `hoursLine` with the stored `holidays` and the live entries of collections shaped like `hourPlans()` (week list, from date, yearly switch), because the schema has no link from hours to its plans.
- D47 (2026-10-15): Publish step (TEMPLATES.md §7.3): on a create task of a drafts collection only the primary button publishes; Enter in a field and Ctrl+S save a draft ("publish by accident" is the blog's must-never). With needsApproval the primary reads "Send for review". An approval after a proposal's scheduled time publishes at once: the server clamps the lapsed `at` to now and writes `history.publishedLate`; a person who publishes themselves with a past time is still refused.

- D52 (2026-10-15): Browser weight. The app's `#ginko/schema` (rendered on the server, shipped to every page) leaves out the editors' texts: labels and slot labels become '', `describe`, `hint`, `group`, `tasks` and `editor` are dropped; choice options keep their labels (nuxt/app-schema.ts). Page and layer code must not read editor texts from it; server routes import the full schema. Core module-level values that translate (`UNSAFE_LINK`, the compiled catalog, a diff fix) are `/* @__PURE__ */`, so the published dist, where core is one shared chunk, lets bundlers drop the catalogs; `pnpm check:pack` fails when a site's first page loads them. The preview listener lives in preview-listener.ts, started by the preview page.
- D53 (2026-10-16): Scheduled file entries. In a file collection with drafts that lists its entries newest first by a date (`drafts: true`, `order: { field, dir: 'desc' }`: posts, a changelog), an entry dated after the build day is left out by `readContent` like a draft; dev shows it. One place keeps it out of every output (pages, lists, feeds, sitemap, llms.txt, `.md` twins, search, prerender). File content is part of the build, so a server-rendered site publishes it with the first build on or after its date too (as Hugo and Jekyll do); sites rebuild daily. Releasing at request time without a build would need a `visible: from` rule in the schema (Studio and server too), not done. The platform keeps its own scheduling (`publishAt`).
- D54 (2026-10-20): `GINKO_CONTENT=platform` (core `siteForContent`) turns a files site into its platform twin (`withoutFiles`) at build and in every CLI command that loads ginko.config.ts, so the build and `ginko release` push the same schema. Unset keeps the config; any other value fails. Why: the hosted template demos deploy the unchanged templates from git with their content in the Studio, and the local Studio gate (gate 7) runs the same way instead of through its own Nuxt layer, which is removed. A real site that moves to the Studio still removes `source: 'files'` in its config (T4); the variable is for running one codebase both ways.
- D55 (2026-10-20): Two hosted platforms from the same code (FILE-01: cms.yml) (FILE-01: demo.yml). `lupinum-ginko-demo` is the showroom and staging: its Vercel project (apps/platform) is linked to main, every template runs there as a site with its content in the Studio (`GINKO_CONTENT=platform`, D54) and its own Vercel project `ginko-template-<name>` (root `templates/<name>`, install `cd ../.. && pnpm install --frozen-lockfile`, build `./node_modules/.bin/nuxt build`: the workspace code of the same commit, not npm, so a site never runs behind the schema its commit released), `.github/workflows/demo.yml` releases each template's schema on every push to main and resets their content from git every Monday (`pnpm templates demo-reset`, `ops:import --reset`). `lupinum-ginko-cms` holds client sites and runs released code only: its Vercel project deploys the branch `cms-production`, which only `.github/workflows/cms.yml` moves to a v* tag after approval in the `cms` environment (no Vercel or Convex credential in GitHub; a run with an older tag rolls back). Clearing a site on a hosted deployment needs `GINKO_DEMO=1` there (seed `importClear`), which only the demo sets, so no key or command can clear a client site. Why: demos must show the newest code and stay fresh after client meetings; client data must never be one wrong key away from a reset.
- D56 (2026-10-22): The template projects `ginko-template-<name>` skip a build unless the template's inputs changed since the commit the project last built: its folder, the workspace packages it imports (not their changelogs, tests or version-only bumps), the root install files and the skip script itself (`node ../../scripts/vercel-ignore-template.ts` as each project's Ignored Build Step; previews stay skipped). A missing earlier commit is fetched, and the build runs when git cannot answer. Why: every push to main built all ten templates, and most pushes change none of them (platform, server, Studio or release commits).
- D57 (2026-10-26): Pictures in a text use the same image path as image fields. A component whose `src` is a library image gets the file's `srcset` and its focus point as `focal` (an `object-position`) from `resolveFileRefs`; the renderer lets exactly these two through for such a component (`IMAGE_EXTRAS`), and the component picks its own `sizes`. Crops stay CSS (`aspect-ratio`, `object-fit: cover`, focus point): one stored file serves every ratio, and a moved focus point shows at once. No AVIF (slow to encode in the upload action; WebP is everywhere), no stored crop rectangles (a second way to crop next to the focus point), no 9:16 for figures. The figure's own edge choice `focus` is retired: a component prop may carry `retired` (the editor's form leaves it out, texts that have it stay valid), unlike a list column.

Release rules follow diffSchema's nearest cases: an added row is a new required field (allowed when the columns' defaults fill it, else refused, as `requiredWithoutDefault`; core/diff.ts `diffFields`), a removed row is a removed field (corrected the same day: a site must be able to change its workdays, and a refusal whose only way out is "keep the row" cannot be followed): allowed when `retired` names it as `'brick.field.row': { drop: true }`, the same place a removed field is stated, and the release then removes the row from every stored entry; without that line it is refused (`rowRemoved`) with one sentence that shows the line to write. A change of `week` that adds or removes days is checked the same way. Rows of `'workdays'` take no field `default` (they follow the week; the columns' defaults fill a new workday). The website reads only the rows the field has, in its order; a backup restore drops a row the field no longer has, with its warning. Two people on different rows of one entry merge in the Studio's conflict panel; a clash on one row stays a conflict. Open: own row labels in label files (the label files carry field labels only; own rows have no user yet, so not now). "min = max with a `unique` column" no longer means a fixed table, and `unique` is gone with its checks and release rules: its only users were the weekday and lunch tables. Stored platform data in the old list shape is converted by the upgrade (checkpoint 6), not read.
