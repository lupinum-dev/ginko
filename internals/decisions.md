# Decisions

A short, dated log of choices a future maintainer or agent might otherwise undo.
Add one line per decision: `Dn (YYYY-MM-DD): decision — why.` Replace a line
when a decision changes; git keeps the history.

- D1 (2026-10-13): Release with the Lupinum OSS `library-monorepo` workflow (Changesets, npm trusted publishing, protected `npm` environment) — every Lupinum repository shares one release, security and CI setup.
- D2 (2026-10-13): `@lupinum/ginko` declares no peer dependency on `@lupinum/ginko-content` — `ginko-content` depends on `ginko`, and a cycle between published packages stops `scripts/release.mjs` from packing. `ginko` still loads `ginko-content` with a dynamic import and tells users to install it; it is only a devDependency (types, tests) and an unbuild external.
- D3 (2026-10-14): Every published package accepts Nuxt 4.6 and Nuxt 5: `nuxt` peer range and module `compatibility` are both `^4.6.0 || ^5.0.0-0` — a site can upgrade Nuxt without upgrading Ginko, and npm installs Ginko next to a Nuxt 5 prerelease without a peer conflict. Proof: `pnpm check:pack --nuxt5` (CI job `nuxt5`) builds every starter and the docs site from the tarballs on the Nuxt 5 nightly that `packages/ginko-i18n/browser/apps/n5` pins. Move that pin forward when a newer nightly is needed; drop the `-0` when Nuxt 5 is released.
- D4 (2026-10-14): Ginko writes all SEO output itself and needs no Nuxt SEO module; the one module every starter gets is `nuxt-og-image` (Takumi), because drawing images is not Ginko's job. With a Nuxt SEO module installed (listed, or through `@nuxtjs/seo`, and not `enabled: false`), Ginko leaves that output to it and hands it the site's data through Nuxt `moduleDependencies` defaults (order-independent; the site's own config wins) and per-request `site-config:init` hooks (language, preview hosts). `nuxt-ai-ready` is turned off while Ginko serves llms.txt — two producers of the same addresses. Share cards on a server need `NUXT_APP_SECRET` (nuxt-og-image signs their URLs); Ginko does not invent one, because Nuxt's sessions use the same secret: create-ginko writes one into `.env` and the build warns without it. Proof: the `docs-seo` site in `pnpm check:pack` (sites/docs with `@nuxtjs/seo`), on Nuxt 4 and Nuxt 5. Code: packages/ginko/src/nuxt/nuxt-seo.ts.
- D5 (2026-10-15): An entry is a page only in the languages it is translated into: `untranslated` defaults to `'hide'` for collections with a `route` and to `'fallback'` without one (`untranslatedMode`), and only a *missing* required translation counts, never an outdated one, a slug or an image description — German text under an /en URL (with `lang="en"` and hreflang) is wrong, while a typo fix in German must not turn a live English page into a 404. Opt-in `'fallback'` on a routed collection lists the entry with a link to its main-language page and gives it no URL in that language. `urlsFor` gives the page URLs (bundle, sitemap, hreflang, publicness); `routeUrls` gives every locale's address for cache refresh and URL clash checks. Code: packages/ginko/src/core/resolve.ts.
- D6 (2026-10-15, Matthias): An outdated translation (its print is of an older main-language text) stays on the site as it is until someone translates it again or confirms it. The Studio marks and lists it. Only a *missing* translation falls back to the main language (`fallback`) or hides a routed entry (D5) — a German typo fix must not turn a live English text German, nor remove the English note on legal pages; the risk that an old fact stays is handled by showing "outdated" where people act (field badge, language-switch line, save message, and the site-wide list). An outdated translation of a text the main language removed entirely goes away with it. `ResolvedEntry` has `outdated: string[]` and `blocking: string[]` (the missing required leaves) instead of `untranslated: boolean`. Code: packages/ginko/src/core/resolve.ts `localized()`, server lib/translation.ts `leafStatus`.
- D7 (2026-10-15): Addendum to D5: a picture's descriptions belong to its file. A save with a new file keeps only the description sent with it (ginko-server lib/content.ts `mergeField`) — an old picture's English text can never describe a new one. On a foreign-language tab the Studio edits only the description.
- D8 (2026-10-15): Addendum to D5 and D6: retired fields never count as outdated translations — core gives retired projections a throwaway `outdated` list, as it does for `blocking`.
- D9 (2026-10-15): An entry's address in another language is made from its translated title while the entry has no page in that language. A save of the title in that language makes the slug there again: the first free one in the brick and language, not taken by a static page or another brick's route. Once the page is online in that language, its address stays. The main-language slug stays as it was at creation. The client never sends a slug (`errors.addressFixed`). Undoing a title save does not bring the old slug back (that language had no page then). A proposal works out the slug when it is applied.
- D10 (2026-10-15): The slug rule for a new entry (per locale from its own text of the `from` field, else the main locale's slug) has one source, core `slugBases`. `entries.create` makes the slugs unique, and the Studio's preview uses them as they are — so the preview shows the address the server will make.
- D11 (2026-10-15): Quick-task sheets edit every language (Opus, option A). A Deutsch/Englisch switch in the sheet; one Speichern stores all languages as whole values of the changed root fields, with no `locale`, so the server needs no change. Why: new dishes, notices and events got no English where they are made, a new event kept a German English address because slugs are fixed at creation, and staff with only a task grant had no way to add English. Consequences: the per-root `fieldRevs` check guards whole-value saves; "Meine behalten" and a restored local copy apply only the person's own languages over the newer state (`ownChangesOver`), so a translation someone else saved meanwhile stays; local copies store their `base`; a per-language form does not offer a copy with texts in another language. Rejected: option B (English fields only in create sheets) and C (a toast that links to Inhalte) — they leave edit-task texts German, and C cannot give a new event its English address; and narrowing a sheet save to `locale` when only one language changed — a second wire format that does not fix `keepMine` on its own.
- D12 (2026-10-15): One entry title on the server. History lines, proposals, search hits, file uses and the agent's labels use core `entryTitle` (through lib/list `titleOf`), the same as the Studio. A planned week is "Woche ab <date>" in the main language. Rows already stored keep the title written at save time.
- D13 (2026-10-15): One rule and one button for a missing translation: "Text auf {name} übernehmen" (text, longtext and Markdown; whole source with a fold) and the tab dot `entry.groupHasGaps` belong to the translation slice. The model slice's own "Gleich wie {name}" version was reverted (e4eae88a, reverted in 236a04c8) — one rule and one button remain.
- D14 (2026-10-15): A picture in a Markdown text stores its own description only when the person wrote one (`![]($file.x)` otherwise). The library's description applies when the site is built, in every language, so a later fix in Dateien reaches every use. A component's `alt` prop stays the component's own text (copied from the library when chosen). Old texts with copied descriptions are not migrated.
- D15 (2026-10-15): Picture captions: option (a). No Markdown title captions, and no change to `GinkoMarkdown` rendering; "Bildunterschrift" in the editor turns the picture into the site's figure block instead.
- D16 (2026-10-15): The editor toolbar decides what fits from its measured width (`ResizeObserver`), not from CSS container queries — the overflow menu is portalled out of any container, and `container-type` on the editor frame would apply layout containment, which places the docked phone bar (`position: fixed`) relative to the frame. The sizes used for the fit sit next to the code and must follow the button classes.
- D17 (2026-10-15): A link to an entry stores the entry's ID (`$<area>.<id>`), not its address, so a later change of the address keeps the link working. The links are unreadable in the Markdown source view; that is accepted. Every import (`ginko import`, `pnpm local:pull`, the Studio backup ZIP) rewrites these links with the new IDs in seed.ts `importRefs`, which also parses the changed texts again and carries the translation prints. Only links in link destinations and reference definitions are rewritten; `$page.` links and code stay as they are.
- D18 (2026-10-15): Staff may change entries they created (Matthias). An entry a staff member creates stores `createdBy`. lib/access.ts `authorize` lets that person change it (never remove it) with a create task of its brick that they still hold; every field is allowed, as when creating. A save goes through a held edit task that covers the changed fields (the widest first) and through the create task only when none does, so an edit task's `needsApproval` keeps applying to the fields it covers; the create task's `needsApproval` applies otherwise. Losing the create grant ends the right. There is no backfill: entries made before this, and all entries of owners and admins, have no creator. The agent door uses the same check: `taskFor` falls back to the create task for own entries, and create-only staff get `ginko_revert` and `ginko_translate`. Backups (`ginko export`) do not carry `createdBy`, because user ids do not move between deployments.
- D19 (2026-10-15): Every staff text that says whom to ask uses "die Person, die dich eingeladen hat" (Opus, option A). The invite mail names that person. A missing right is shown muted, never in error red.
- D20 (2026-10-15): People's names (Opus, option B). Each person has one display name in `userSettings.name`, which only that person sets (Meine Seiten, or the invite page). Everyone in a team sees it, staff included. Owners and admins also see emails: they see "Name (E-Mail)" wherever a member is named (history, conflicts, files, keys, review, the proposal digest mail). Staff see a colleague's name, or "Ein Mitglied" when there is none, and never an email; the address alone shows until a name is set. The reader always sees themselves as "Du" (Who `{ self: true }`). Why: a name is whatever the person typed; the address is the identity they verified. Deleting the account deletes the name with `userSettings`. No names for former members or for platform admins who are not members.
- D21 (2026-10-15): Backup in the Studio (Matthias: backup in the Studio; Opus: option A, the ZIP is built in the browser): the browser builds the ZIP with client-zip from the public query `backup.download` (owners and admins; the same `snapshotOf` as GET /export), so a Studio backup and `ginko export` share one format (`pathOf` and `defaultDir` from `@lupinum/ginko/internal`). It streams to disk in Chromium; other browsers hold up to 1 GB in memory. No server-side ZIP job.
- D22 (2026-10-15): `grantGroups(schema, grants)` in `@lupinum/ginko/internal` is the one way to read grants as rights by area: Team page, invite mail and invite page use it, so the three cannot disagree.
- D23 (2026-10-15): Proposal outcome (Opus): the author gets an email only on rejection — the reason, plus a link that reopens the proposal (`/s/{slug}?task=…&reopen=…`; for an assistant's proposal the link goes to Verlauf). No email when approvers reject their own agent's proposal. No email on approval.
- D24 (2026-10-15): A save that becomes a proposal replaces (withdraws) the author's older open save on the same entry only when both have the same task, the same door (ui/agent) and the same language, and the new one writes every root field of the older one (confirmed leaves count by their root). Otherwise both stay open. The withdrawn proposal gets `decidedBy` = author. Why: the sheet starts from the open proposal, so the new one includes it; two open proposals for the same fields made one of them stale when approved.
- D25 (2026-10-15): Sign-out with local unsaved input (N2b, option A): Abmelden asks first when this browser holds unsaved input of this person (`window.confirm`: "In diesem Browser sind noch ungespeicherte Änderungen. Beim Abmelden werden sie gelöscht. Trotzdem abmelden?"). OK signs out and deletes only this person's copies, so shared computers stay clean; Abbrechen keeps everything. No question when nothing is stored; only copies that would still be offered back count (less than 14 days old). A refused sign-out keeps the session and the copies and says "Abmelden hat nicht geklappt." A session that ended elsewhere (revoked, expired, other devices signed out) keeps the copies for the next sign-in. Konto löschen deletes them without asking. (Also belongs in internals/v7-experience-decisions.md next to N2.)
- D26 (2026-10-15): One name per Studio screen. The nav words (Heute, Inhalte, Prüfen) are also the page titles, and a view has a single label key, so the names cannot drift apart again.
- D27 (2026-10-15): The reminder rule has one home: lib/reminders.ts exports `isReminded` and `reminderBricks` (weekly tasks and status lines). `sites.mine` uses them for `weekly`, so the Studio offers the reminder switch exactly where a mail can come.
- D28 (2026-10-15): A collection with `plans` holds one live entry per value of `plans.field`. `create`, a save that changes that field, `restore` and `undo` refuse a second one with INVALID (`errors.pleaseCheckMarkedFields`; the issue sits at `plans.field` with key `errors.weekAlreadyPlanned`). The trash does not count. This applies to agents too — a week has one plan, and none of these doors may make a second.
- D29 (2026-10-15, Matthias): Company data in the agency preset is one single, `company()` ("Firmendaten"). Every field is optional, so the release check (`singleWithoutDefault`) lets a live site add it. Name, address, register number and VAT ID are the same in every language; country and court are translated. One edit task covers all fields, the site's extras included. Sites build `tel:` links with `telHref()`. The legal components of a site read this single and type no address themselves. The provider box is called "Anbieter und Medieninhaber", and the typed Medieninhaber line is deleted (option a). The field's describe reads (de) "Name, Anschrift und Kontakt deiner Firma, zum Beispiel für das Impressum. Steht eine Angabe auch im Text einer Seite, änderst du sie dort." / (en) "Your company’s name, address and contact details, for example for the imprint. Where a detail also appears in a page’s text, change it there." Mentions typed into page text (emails in legal texts, SEO descriptions) are not linked to Firmendaten.
- D30 (2026-10-15): Reading time is computed, never typed: `max(1, round(wordsOf(body) / 200))` minutes. Page state carries each Markdown field as `{ ref, words }` (`withMarkdownRefs`), and the public `wordsOf(value)` gives the same count for a tree and for its ref, so lists use the word count carried on the ref. The agency blog has no `readingTime` field.
- D31 (2026-10-15): The agency preset declares only fields a site reads. Removed: services and case studies "Hervorgehoben", "Passende Leistungen" (and the `servicesBrick` option), "Position auf der Startseite", the FAQ "Kategorie" and "Lesezeit". "Bereiche" (`serviceCategories`) is the one source for which service a case study belongs to (option a). The homepage selection is a site single with an ordered list of at most 3 case studies, not a number on each entry (option a). A site that groups FAQ adds a choice through `extra`.
- D32 (2026-10-15): v7 company data: Firmendaten (`company()` from the agency preset, key `firma`) is the one source for legal name, address, contact and register data. v7 reads it with `useCompany()`, which adds `phoneHref` and `addressLines`. site.config.ts keeps only brand and technical facts (name, url, ogImage, areaServed, forms, social). The provider box is "Anbieter und Medieninhaber" and the typed Medieninhaber line is deleted (option a). AGB 13.1 and the customer privacy notice use `::business-contact`. "Inhaber: …" and "Website: …" stay typed text. Every line shows only when it has a value.
- D33 (2026-10-15): v7 homepage projects: one `startseite` single holds an ordered list of at most 3 refs to `referenzen` (option a). `homeOrder` and `featured` are gone. The site skips a selected case study that was removed or hidden, and a repeated pick, so the homepage never shows an empty or doubled card.
- D34 (2026-10-15): The `planned` brick rule (core, option A, Opus). `planned: { field, next, from }` on single and collection: from the date in `from`, `next` replaces `field`. `next` and `from` are optional and set together. Every edit task that changes `field` must show both (`checkSchema`). The site applies the plan (gastro `priceOn`). The platform keeps value and date together, opens tasks on the value in effect (prefill rollover) and says from when a plan-only save shows. In the typed builder `from` is only a field name, because a factory with generic fields cannot name its date field; `checkSchema` reports a `from` that is not a date.
- D35 (2026-10-15): Rules across fields (a plan set by halves, a week start) bind only what is written now. They are errors in create, and in patch when the save touches one of their fields. Stored data that breaks them gives warnings in release and restore. Why: a platform release re-validates every entry of a brick whose fields changed, labels included, so an old half plan or a stored Thursday week must not block a release.
- D36 (2026-10-15): The weekly task (the edit task that presets a date to `@workWeek`) always covers the current work week. The server refuses any other week through it (`errors.weeklyTaskThisWeek`), and a proposal from an earlier week goes stale on approval. The field that holds a week start (core `weekStartField`: `plans.field`, else the weekly task's field, else a date preset to `@workWeek` or `@nextWorkWeek`) must hold the first day of a week (`issues.notWeekStart`).
- D37 (2026-10-15): An `@today` prefill keeps a stored date that has not passed (stored >= today). Why: reopening "Heute geschlossen" moved tomorrow's closure to today. This applies to every edit task with `@today` (`hours.closedToday`, industrie's `closedOn`, `menu.soldOut`). Week tokens (`@workWeek`, `@nextWorkWeek`) always give the task's week. The agent door resolves the prefill the same way.
- D38 (2026-10-15): Gastro availability (option A, slimmed): `menu.onMenu` (optional boolean, default true, inside "Gericht bearbeiten", no separate season task), `menu.soldOutOn` (optional date; quick task "Gericht heute aus", the first menu task, prefilled `@today`; it resets by itself the next day), `events.soldOut` (optional boolean; quick task "Veranstaltung ausgebucht"). They are optional, not required with a default, because the files reader does not fill defaults: a required field would make existing Markdown menus invalid. A missing value means on the menu, not sold out, and bookable. `dishOn(dish, date)` is the one rule for the site (menu page, allergen key, JSON-LD menu). A fully booked event shows "Ausgebucht" instead of the booking link; in JSON-LD its offer has availability `SoldOut` and no booking URL.
- D39 (2026-10-15): The restaurant demo's imprint takes the provider block (house name, address, phone, email) from the contact brick ("Adresse und Kontakt"), so a move updates it. The owner's Markdown holds only the legal details: owner, business purpose, UID, trade authority, chamber, trade law and the § 25 MedienG disclosure. This matches the agency preset's "Firmendaten" decision (D29); once that single exists in the restaurant, it can follow the same pattern.
- D40 (2026-10-15): preset-gastro API: `upcomingPlans` returns an optional `ends` (additive, minor). A yearly season that runs over New Year ends in the year after its start.
- D41 (2026-10-15): `closedOnClosure(hours, today)` is the one rule that turns a `closedOn` day after today into a closure. `upcomingClosures` adds the days limit on top; a table of all closures ahead calls it directly.
- D42 (2026-10-15): Glossary for the gastro preset: one word per concept — Veranstaltungen (Events), Nachspeisen (Desserts), Öffnungszeiten ab Datum (Opening hours from a date), Holiday closures and exceptions. Only labels changed; values, keys and task ids stay.
- D43 (2026-10-15): Templates infrastructure (ginko-internal specs/TEMPLATES.md T3, T10). `templates/*` are workspace members; root `overrides` link the fixed group to `workspace:*`, and `bumpVersionsWithWorkspaceProtocolOnly` keeps `changeset version` from rewriting a template's committed range (`^A.B.0` of the next release per `changeset status`). Inside the repository a template's scripts run from the root (`pnpm --filter <name> run …`): its own pnpm-workspace.yaml (allowBuilds, for users) makes pnpm treat its folder as a separate root. create-ginko without `--template` keeps the plain starter (`template/`), and `--preset` keeps `presets/`, until templates replace them. Locale pruning needs one locales list (`app/routes.ts`, else `ginko.config.ts`); URL prefixes derive from it in code, so a main-language swap renames content files only. The platform-ready gate strips `source` in scripts/templates.ts until core has `withoutFiles`.
