## Set the locales

The locales of a site are in `locales` in `ginko.config.ts`. Any canonical language tag is allowed, for example `'es'`, `'pt-BR'`, or `'zh-Hant'`. The tag is also the prefix in the address (`/pt-BR/…`). The first locale is the **main locale**. Its pages have no prefix; the other locales get one:

```ts
export default defineSite({
  site: 'restaurant',
  locales: ['de', 'en'],   // /speisekarte (de) and /en/menu (en)
  // …
})
```

You do not install an i18n module yourself. The Ginko module installs **ginko-i18n** (`@lupinum/ginko-i18n`) and gives it the locales from the configuration. The main locale is the default locale, and `url` is the base for canonical and hreflang links. Do not install `@nuxtjs/i18n` as well.

ginko-i18n takes the locale from the address. No cookie and no browser header changes the locale of a page with a localized address. One exception is for apps behind a login: the paths you list in `userLocale` follow the user instead (the cookie `ginko_locale`, then the `Accept-Language` header), and `/api/**` always does. `userLocale` is an option of ginko-i18n. You set it under `i18n` in `nuxt.config.ts`; the Ginko module passes the other `i18n` options through:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  i18n: { userLocale: ['/app/**'] }, // these paths have no language prefix
})
```

ginko-i18n sets `lang`, `dir`, `canonical`, `hreflang`, and `og:locale` on every page.

The texts of the content are stored per locale. If a translation is missing, the bundle shows the text of the main locale. See "Reading content", section "Fallback".

## Page paths per locale

A page file sets the path of the main locale. The file `app/pages/speisekarte.vue` is `/speisekarte`. For other locales, you set your own path with `definePageMeta`:

```vue
<!-- app/pages/speisekarte.vue -->
<script setup lang="ts">
definePageMeta({ i18n: { paths: { en: '/menu' } } })
</script>

<template><PageMenu /></template>
```

The English page has the path `/en/menu`. ginko-i18n adds the prefix `/en` itself. Without this setting, the English path is `/en/speisekarte`.

Also list every fixed path in `pages` in `ginko.config.ts`, with the prefix:

```ts
pages: {
  home: { de: '/', en: '/en' },
  menu: { de: '/speisekarte', en: '/en/menu' },
},
```

Ginko uses `pages` for the sitemap and for refreshing pages on demand.

## useI18n

`useI18n()` gives you the tools for texts and the language switcher:

| Name | Meaning |
| --- | --- |
| `t(key, params)` | Returns a text from the message files. |
| `locale` | The current locale. |
| `localePath(path, locale)` | Returns the path of a page in a locale. The locale is optional. |
| `alternates` | The current page in every locale, for the language switcher. |

`localePath` takes the path of the main locale: `localePath('/speisekarte')` returns `/speisekarte` in the main locale and `/en/menu` in the English version. Use `localePath` only for pages of your own site. For the detail pages of entries, use the addresses from the bundle (`item.url`, or `item.urls` for every locale).

A language switcher from `alternates`:

```vue
<script setup lang="ts">
const { alternates } = useI18n()
</script>

<template>
  <nav aria-label="Language">
    <NuxtLink
      v-for="a in alternates"
      :key="a.code"
      :to="a.path"
      :hreflang="a.language"
      :aria-current="a.current ? 'true' : undefined"
    >
      {{ a.code.toUpperCase() }}
    </NuxtLink>
  </nav>
</template>
```

## Message files

Fixed texts of the site, such as navigation and labels, live in `i18n/<locale>.json` next to `nuxt.config.ts`. These are not content from Ginko bricks. You create one file per locale:

```json [i18n/de.json]
{
  "nav": { "menu": "Speisekarte" },
  "weekOf": "Woche ab {date}"
}
```

```json [i18n/en.json]
{
  "nav": { "menu": "Menu" },
  "weekOf": "Week of {date}"
}
```

```vue
<script setup lang="ts">
const { t } = useI18n()
</script>

<template>
  <h1>{{ t('nav.menu') }}</h1>
  <p>{{ t('weekOf', { date: 'October 5' }) }}</p>
</template>
```

The texts use the ICU format. With it you write, for example, plural rules: `{count, plural, one {# dish} other {# dishes}}`. If a key is missing in a locale, the site shows the text of the default locale. Check the files with `npx ginko-i18n check`.

For a text with a link or emphasis, write tags in the message, for example `"I accept the <link>privacy policy</link>."`. `<I18nT>` fills each tag through a slot of the same name:

```vue
<script setup lang="ts">
const { localePath } = useI18n()
</script>

<template>
  <I18nT k="legal.consent">
    <template #link="{ text }"><NuxtLink :to="localePath('/privacy')">{{ text }}</NuxtLink></template>
  </I18nT>
</template>
```

Every feature of ginko-i18n (date and number formats, `getI18n` in server routes, the rules for links) is in the [ginko-i18n README](https://github.com/lupinum-dev/ginko/tree/main/packages/ginko-i18n#readme).

## Detail pages

An entry can have a different address in each locale. The bundle delivers these addresses in `urls`. The page file has one path per locale, with the placeholder `:slug()`:

```vue
<!-- app/pages/docs/[slug].vue -->
<script setup lang="ts">
definePageMeta({ i18n: { paths: { de: '/doku/:slug()', en: '/docs/:slug()' } } })
const route = useRoute()
const doc = useGinkoEntry('docs', () => route.params.slug)
</script>
```

The path must match the `route` of the brick. There it is `/doku/[slug]` for German and `/en/docs/[slug]` for English.

You do not need to write `alternates` for detail pages. The Ginko module reports the addresses of an entry from the bundle to ginko-i18n. So the language switcher points to the right address in the other locale, and `hreflang` is correct. If an entry has no page in a locale, that page counts as not translated there.

Use `missing` in the brick to control what happens when a translation is missing:

- `'fallback'` (default) shows the entry in every locale. If the slug is missing, the slug of the main locale applies.
- `'hide'` hides the entry in a locale when a translatable required field is missing or outdated there.

::callout{type="note"}
For file bricks, an existing translation is always current. A missing file triggers the fallback or hides the entry, depending on `missing`.
::
