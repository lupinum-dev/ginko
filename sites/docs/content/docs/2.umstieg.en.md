## Ginko or Nuxt Content

Both read Markdown from `content/` and render it in a Nuxt site. They solve different jobs.

**Take Ginko** when people who are not developers edit the site. The same brick can come from files today and from the platform tomorrow: the site code stays the same. Owners edit in the Studio, with approval, a schedule, history, and a link check before anything goes live. Languages, addresses per language, and hreflang come with it.

**Take Nuxt Content** when only developers edit, in Git, and you need what Ginko does not have: Nuxt Studio, or more than 500 entries in one collection (Ginko's limit). Ginko has [data files in YAML, JSON and CSV]($docs.inhalte-aus-dateien#data-files-yaml-json-csv) and queries with `where`, `order` and `limit` too.

A site can also start with Ginko file bricks only. It then needs no platform and no account.

## From Nuxt Content

| Nuxt Content | Ginko |
| --- | --- |
| `content.config.ts` with `defineCollection` | `ginko.config.ts` with `collection({ source: 'files', … })` |
| a `schema` with Zod | fields with `f.*`: `f.text`, `f.markdown`, `f.image`, … |
| `queryCollection('docs').path(path).first()` | `useGinkoEntry('docs', slug)` |
| `queryCollection('blog').where(…).order(…).all()` | `useGinkoQuery('blog', { where, order, limit })` |
| `queryCollectionNavigation` | `useGinkoNav(['docs'])` |
| `queryCollectionItemSurroundings` | `useGinkoNeighbors('docs', id)` |
| `queryCollectionSearchSections` | the search index at `/__ginko/search/<locale>.json` |
| `<ContentRenderer :value="page" />` | `<GinkoMarkdown :value="doc.data.body" />` |
| MDC `::callout` | the same syntax; you map names to components with `:components` |
| `useSeoMeta` per page | `useGinkoSeo({ … })` |

What changes when you move:

- **One file per entry and language.** `1.einstieg.md` is the main language, `1.einstieg.en.md` the translation. See [Content from files]($docs.inhalte-aus-dateien).
- **Frontmatter is checked.** A key the brick does not know stops the build, with the file and the field in the message.
- **Queries read the bundle.** `useGinkoQuery` runs on the data of the page, not on a database. `where` takes `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, and `contains`; `order` is a text like `'date desc'` or an object like `{ field: 'date', dir: 'desc' }`.
- **Links between entries follow the language.** In Markdown, `[Bricks]($docs.bausteine)` points to the entry in the language of the page. A link that points nowhere stops the build.

## From @nuxtjs/i18n

The Ginko module installs **ginko-i18n** and gives it the locales of the site. Remove `@nuxtjs/i18n`: setup stops with a message when both are installed.

| @nuxtjs/i18n | ginko-i18n |
| --- | --- |
| `i18n: { locales, defaultLocale, strategy }` in `nuxt.config.ts` | `locales` in `ginko.config.ts`; the first one is the default |
| `$t('key')`, `useI18n().t` | `useI18n().t` |
| `useLocalePath()` | `useI18n().localePath` |
| `useSwitchLocalePath()`, `useLocaleHead()` | `useI18n().alternates`; head tags are set for you |
| `defineI18nRoute({ paths })` | `definePageMeta({ i18n: { paths } })` |
| `i18n/locales/*.json` with vue-i18n syntax | `i18n/<locale>.json` with ICU syntax |
| `detectBrowserLanguage` | `useLocaleSuggestion()`: a link the visitor can choose |

What changes when you move:

- **Plurals use ICU.** `'no dish | one dish | {count} dishes'` becomes `'{count, plural, =0 {no dish} one {# dish} other {# dishes}}'`.
- **Two strategies.** `prefix_except_default` (the default) and `prefix`. Domains per language and `no_prefix` do not exist.
- **The address decides the language.** No cookie and no browser header switches a page. For apps behind a login, `userLocale` lets chosen paths follow the user instead.
- **Detail pages need no extra code.** The addresses of an entry in each language come from the bundle, so the language switcher and hreflang are right without `setI18nParams`.

The details are in [Languages]($docs.sprachen).
