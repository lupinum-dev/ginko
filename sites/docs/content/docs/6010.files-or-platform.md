Every brick has one source. With `source: 'files'`, its content is files in the repository. Without it, its content is on the platform. You decide per brick, and a site can mix both.

```ts [ginko.config.ts]
bricks: {
  legal: single({ label: 'Legal notice', source: 'files', fields: { /* … */ } }),   // files
  hours: single({ label: 'Opening hours', fields: { /* … */ } }),                   // platform
}
```

## The difference

| | Files | Platform |
| --- | --- | --- |
| Where the content is | `content/` in the repository | The platform, which you [host yourself]($docs.host-the-platform) |
| Who changes it | A developer, in an editor | An owner or staff, in the Studio, also on a phone |
| How a change goes live | A commit and a deploy | An owner presses "Publish". The site shows the change within 60 seconds. |
| History | git | The Studio keeps every version and can undo |
| Approval, schedule, quick tasks | no | yes |
| What the site needs | Nothing. A static host is enough. | A server, the platform address, and a site on the platform |
| A schema change | Change the config and the files in one commit | `ginko release`, and the schema only grows |
| When the source is not reachable | Cannot happen: the content is part of the build | The page answers 503, and the host keeps the last good page |

## What stays the same

The code of a page. `useGinko('hours')` reads a file brick and a platform brick in the same way, with the same types. Fields, checks, translations, date limits, links and search work for both.

So the source is a decision you can change. A text can start as a file while you build the site and move to the platform when the owner takes over.

## How to choose

Ask who changes the content, and how often.

**Take files when:**

- a developer writes the content: docs, a blog of the team, legal pages
- the content changes with the code, such as a changelog
- the site should run on a static host, without a server
- you have no access to the platform

**Take the platform when:**

- a person without a code editor changes the content: opening hours, a menu, events, job ads
- a change must go live in a minute, without a deploy
- a second person should approve a change, or a change should start on a date

Many sites use both: the pages that sell are files, the facts that change every week are on the platform.

## What changes when a brick moves to the platform

- **The content moves once.** The platform does not read your files. A single starts with the `default` of each field, and a collection starts empty. You type the content into the Studio, or move many entries from files with `ginko files-export` and `ginko-platform import`: see [A website with content in files]($docs.connect-a-website#a-website-with-content-in-files).
- **Required fields of a single need a `default`.** The platform must be able to create the single before anyone has typed. `f.markdown`, `f.image` and `f.file` have no default: make them optional.
- **The schema is released.** `ginko release` sends the schema to the platform before the deploy. From then on, the schema only grows: you retire a field, you do not delete it. See [Schemas only grow]($docs.schemas-only-grow).
- **The site needs a server.** A static build no longer fits, because the content changes after the build.
- **The files stop counting.** Remove the files of the brick from `content/`, so that nobody edits them by mistake.

[Move a brick to the platform]($docs.move-a-brick-to-the-platform) has the steps.

## The way back

`ginko export` saves the schema, all entries and all files of a site to a folder. That folder is a backup in the format of Ginko, not the layout of `content/`: to make a platform brick a file brick again, you write the files from the export yourself. See [Export and back up]($docs.export-and-backup).
