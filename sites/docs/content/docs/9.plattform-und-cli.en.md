## What owners do on the platform

The platform is a hosted web app. It turns your bricks into forms and stores the content. The site fetches the content from it as a bundle.

- **Sign-in.** People sign in with a code that arrives by email. An account exists only by invitation.
- **Roles.** An **owner** (`owner`) may do everything on their site and invites staff. A **staff member** (`staff`) may only do the tasks that the owner grants. An **admin** may do everything on all sites.
- **Editing.** Owners change entries in forms. Tasks from the bricks are shortcuts for frequent chores. A preview shows the real site with the changed content.
- **Safety.** If two people change the same field, the platform detects the conflict. A change can be undone. Deleted entries can be restored for 30 days.
- **Translations.** If someone changes a text in the main locale, the translation counts as outdated. The site then shows the main-locale text until someone confirms or rewrites the translation.
- **Refresh now.** The site reloads content at most every 60 seconds. An owner can have a site reload at once, for example to take an entry off the site.

You, the developer, define the bricks. The owners fill them.

## The CLI

`ginko` is a command in the package `@lupinum/ginko`. The commands load your `ginko.config.ts` (default: `./ginko.config.ts`). Use `--config <file>` to name another file. The messages of the CLI are in German. In a project, you start it with `pnpm exec ginko <command>` or from a script in `package.json`.

::code-group
```bash [pnpm]
pnpm exec ginko dev
```
```bash [npm]
npx ginko dev
```
```bash [yarn]
yarn ginko dev
```
::

These environment variables control the commands:

- `GINKO_PLATFORM`: the address of the platform.
- `GINKO_KEY`: a push key of the site, in the form `ginko_<site>_<32 characters>`. It has scopes: `release`, `check`, `export`, and `pull`. The platform stores only its hash.
- `GITHUB_SHA`: the commit that a release builds. Only `release` needs it.

### ginko dev

```bash
ginko dev
```

`ginko dev` starts everything locally: a local Convex backend, the platform, and your site with `nuxt dev`. It sends your schema to the local platform, right away and after every change of `ginko.config.ts`. Rejected changes appear as a warning but go through. So you can experiment freely locally. If a file that the configuration imports changes, you must restart `ginko dev`. Ctrl-C stops all processes.

`ginko dev` runs only in the Ginko monorepo, because it needs `apps/platform`. For a site with only file bricks, `nuxt dev` is enough.

### ginko pull

```bash
ginko pull
```

`ginko pull` copies the content of production into the local platform. It runs `export`, then `import`. So you test with real content. The command needs `GINKO_PLATFORM` and `GINKO_KEY` with the scope `pull` or `export`. It runs only against the local platform and stops if the target is not local. It replaces the content of the site locally.

### ginko check

```bash
ginko check
```

`ginko check` checks your configuration against production and writes nothing. It shows the allowed changes, new migrations, and the size of the content. It reports every rejection with a hint on how to solve it. On an error, it exits with code 1. Use it in CI on every pull request.

`ginko check` also checks the links in your content. It asks external links (`http://…` and `https://…`) only if you set `links: { external: 'error' }` (or `'warn'`). It requests each address once and reports only sure cases: 404, 410, an unknown host, or two timeouts. Answers such as 403 or 429 do not count, because many sites block bots. Ginko remembers good results for seven days in `node_modules/.cache/ginko`. The same check runs on `nuxt build` and `nuxt generate`, never in dev mode. Without the option, Ginko makes no network request.

### ginko release

```bash
ginko release
```

`ginko release` brings schema and content to production. You run it in CI on `main`. It does the following:

1. It checks whether `GITHUB_SHA` is still the newest commit of `main`. If not, it prints `{"deploy":false,"reason":"superseded"}` and exits with code 0.
2. It loads the state of production and checks your schema (see below).
3. It runs migrations and checks all entries.
4. It writes everything in one step. If production changed in the meantime, it retries up to five times.

On success, it prints `{"deploy":true,"schemaRev":…,"contentRev":…}`. Deploy the site only when `deploy` is `true`. Repeating the same release with the same commit is safe.

### ginko export and ginko import

```bash
ginko export --out ginko-export-my-site
ginko import ginko-export-my-site
```

`ginko export` saves the schema, all entries (deleted ones too), and all files of production into a folder. The folder must be new or empty. Without `--out`, it is called `ginko-export-<site>-<yyyy-mm-dd>`. It contains `export.json` and the folder `files/`. `export.json` is written last: a folder with this file is complete. The command prints one JSON line with the number of entries and files. It needs a key with the scope `export` or `pull`. Run it weekly in CI and upload the folder as an artifact.

`ginko import <folder>` loads an export into the local platform. It replaces the entries of the site there. People are kept. It runs only locally and stops before it writes anything if the target is not local. Use it to check that a backup can be restored.

## Schemas only grow

A schema in production may only grow. Content belongs to people, and older versions of your site still read the old schema. So `ginko check` and `ginko release` reject changes that could break data or old code. The rule: everything that is not explicitly allowed is rejected.

**Allowed:**

- new bricks
- new optional fields
- new required fields with a `default`, or with a migration that fills them
- new options in `choice` and `choices`
- a higher `max` and a lower `min`
- new texts: `label`, `hint`, `describe`, `itemLabel`, option labels
- new locales at the end of `locales`
- changes to `pages`, `tasks`, `order`, `visible`, `missing`, and `autoRemoveExpired`

**Rejected:**

- a field or brick that is missing (do not rename, do not delete)
- a different type
- an optional field that becomes required
- a removed option
- a lower `max`, a higher `min`
- a changed translatability, `step`, `currency`, `route`, `timezone`, or main locale
- a removed locale
- a changed `default`

So there is **no rename** and **no type change**. To replace a field, you add a new one, fill it with a migration, and retire the old one:

```ts
export default defineSite({
  // …
  bricks: {
    menu: collection({
      label: 'Menu',
      fields: {
        headline: f.text('Headline'),   // stays unchanged in fields
        title: f.text('Title'),         // new required field
      },
      max: 150,
      order: 'manual',
    }),
  },
  // The old field keeps showing the current value of title in the bundle.
  retired: { 'menu.headline': { from: 'title' } },
  migrations: {
    '2026-11-title-from-headline': {
      brick: 'menu',
      fills: 'title',
      from: (entry) => entry.headline,
    },
  },
})
```

- `retired` retires a field. It disappears from the editor. It stays in the bundle, so older versions of the site keep working. `from` mirrors the value of another field. With `value`, you set a fixed value. An optional field needs no rule (`{}`).
- A migration is a pure function. It has no access to the network, the clock, or randomness. It runs in `ginko release` on your machine or in CI, never on the platform. Its ID looks like `2026-11-name`. You must not change a known migration.

::callout{type="warning"}
A schema release cannot be taken back. Run `ginko check` first. If you really want to replace a field, plan the three steps (new field, migration, retire the old field) into one release.
::

Bricks with `source: 'files'` are not part of the schema of the platform. This rule does not apply to them.
