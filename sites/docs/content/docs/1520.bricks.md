This page lists every setting of a brick. A brick is one kind of content in `ginko.config.ts`; [Model your content]($docs.model-your-content) shows how to write one. The field types have [their own page]($docs.field-types).

## Single and collection

A brick describes one type of content. There are two kinds:

- `single` is a **single**: exactly one entry. Examples: opening hours, imprint, contact details.
- `collection` is a **collection**: many entries with the same fields. Examples: dishes, events, notices.

Both go under `bricks` in `defineSite`. The key is the name of the brick. It starts with a lowercase letter and contains only letters and digits, for example `menu`.

```ts
import { collection, defineSite, f, single } from '@lupinum/ginko'

export default defineSite({
  site: 'restaurant',
  name: 'Gasthaus zur Linde',
  url: 'https://ginko-demo-restaurant.vercel.app',
  timeZone: 'Europe/Vienna',
  week: { firstDay: 'mo', workdays: ['mo', 'tu', 'we', 'th', 'fr'] },
  locales: ['de', 'en'],
  currency: 'EUR',
  pages: { home: { de: '/', en: '/en' }, menu: { de: '/speisekarte', en: '/en/menu' } },
  bricks: {
    contact: single({
      label: 'Address and contact',
      fields: {
        street: f.text('Street and number', { max: 80, translate: false }),
        phone: f.text('Phone', { format: 'tel' }),
      },
    }),
    menu: collection({
      label: 'Menu',
      fields: {
        name: f.text('Name', { max: 120 }),
        price: f.money('Price'),
      },
      max: 150,
      order: 'manual',
    }),
  },
})
```

Both functions take these settings:

| Setting | Applies to | Meaning |
| --- | --- | --- |
| `label` | both | Name of the brick in the editor. Required. |
| `describe` | both | Short explanation in the editor, a text or a text per language like `label`. Bricks and components say what they are for with `describe`; a field has `hint` for the help text under it. |
| `fields` | both | The fields of the brick. Required. |
| `source` | both | `'files'` reads the brick from Markdown files. Without it, the brick comes from the platform. |
| `tasks` | both | Tasks for the editor. See below. |
| `layout` | both | `'tabs'` shows field groups as tabs (see [Groups and tabs](#groups-and-tabs)). |
| `max` | collection | Largest number of entries, 1 to 500. Required. |
| `order` | collection | Order of the entries. Required. |
| `route` | collection | Address of the detail pages, per locale. |
| `visible` | collection | When an entry is visible. |
| `untranslated` | collection | What happens when a translation is missing: `'hide'` (default with `route`) or `'fallback'` (default without `route`). See [Missing translations]($docs.missing-translations). |
| `publishedOn` | collection | The date field that holds the day an entry was published, such as `'date'` on posts. It never hides an entry: a file entry waits for `$publishAt`. `ginko check` notes a date after today on an entry without `$publishAt`, and a date before the day of its `$publishAt`. |
| `plans` | collection | Entries plan weeks of a single brick ahead. |
| `status` | both | One status line on the Studio's Today page: `{ next: 'when' }` (next entry by a date field), `{ count: true }` (entries that end within 7 days; needs `visible`), `{ missing: 'image' }` (entries without an optional field), `{ age: 'date' }` (newest entry and its age), or on a single a status rule of a pattern, `{ rule: 'opening-hours' }` (today's opening hours; `hours()` sets it). A line that needs doing is mailed with the weekly reminder. |

Limits of one site: at most 30 bricks, and at most 60 fields per brick.

## Field types

You build a field with `f.<type>('Label', options)`. The label is the name of the field in the editor. Without `optional: true`, a field is required.

```ts
name: f.text('Name', { max: 120 }),
price: f.money('Price', { optional: true }),
```

[Field types]($docs.field-types) lists every type with its options, defaults, limits and the value the site reads.

Four notes go beyond a single field:

- **Markdown attributes.** Raw HTML always stays text. Attributes in curly braces take `title`, `lang`, `dir` and `aria-*` (`**neu**{lang="de"}`), plus what the element needs, such as `target="_blank"` on a link or `width` and `height` on an image. A component takes the props its registry declares. Anything else, such as `class`, `data-*`, `style`, `id` or `onclick`, is refused. Only Markdown and its plugins set classes (task lists, footnotes, code): with a class of its own, a text could take a CSS rule of the site and, for example, lay an invisible link over the whole page.
- **Country and public holidays:** `country` in the site config is the site's country (ISO 3166-1, e.g. `'AT'`). It is the country of JSON-LD addresses that have none, and it picks the public holidays of the opening hours: Ginko knows `AT`, `DE` (nationwide days only) and `SG`; another country counts no public holidays (`ginko check` warns). `calendar` overrides it: `'AT'`, `'DE'`, `'SG'`, `'none'`, or your own function `(year) => holidays`. The schema stores the result as `holidays`, so the Studio and the reminder mail count the same holidays as the site. Pages read `country` with `useRuntimeConfig().public.ginko.country`.
- **Images and files** are uploaded in the editor on the platform. The bundle holds the URL. For images, Ginko also makes WebP copies 480, 960 and 1600 px wide (only those smaller than the image), at upload on the platform and at build for files. `<GinkoImage>` offers them to the browser with `srcset`, so phones load small files.
- **Platform-managed properties.** The stored types `Field` and `Brick` also have `pos` and `retired`. The platform sets them; `f.*`, `single` and `collection` do not take them. To retire a field, use `retired` in the site config (see [Schemas only grow]($docs.schemas-only-grow)).

## Groups and tabs

A long form is easier to fill in parts. Give fields a `group`; the Studio shows each group under its heading. With `layout: 'tabs'` on the brick, the groups become tabs on wide screens. Phones always show headings. Fields without a group come first. Groups only change the form: the data stays the same.

```ts
legal: single({
  label: 'Legal',
  layout: 'tabs',
  fields: {
    imprint: f.markdown('Imprint', { group: 'Imprint' }),
    privacy: f.markdown('Privacy', { group: 'Privacy' }),
  },
}),
```

After a refused save, a tab with an error shows a red dot and opens first.

## Routes and slugs

A collection gets detail pages when it has a `route`. The route names one path per locale, with `[slug]`:

```ts
events: collection({
  label: 'Events',
  fields: {
    title: f.text('Title', { max: 120 }),
    slug: f.slug('Address', { from: 'title' }),
    when: f.daterange('When'),
  },
  max: 30,
  order: { field: 'when', dir: 'asc' },
  route: { de: '/veranstaltungen/[slug]', en: '/en/events/[slug]' },
})
```

These rules apply to a route:

- You must give a path for every locale in `locales`. Each path starts with `/` and contains `[slug]`.
- The path already includes the locale prefix, for example `/en/events/[slug]`.
- The brick needs an `f.slug` field. Its option `from` names the text field that the slug comes from.
- Only collections have slugs. A single with a slug field is an error.

The slug is made once, when an entry is created. Ginko writes ä, ö, ü, and ß as ae, oe, ue, and ss, uses lowercase letters, and joins words with `-`. A duplicate slug gets `-2`, `-3`, and so on. After that, the slug stays fixed. Each locale has its own slug. For file bricks, the slug comes from the frontmatter or the file name (see "Content from files").

You write the page for the route yourself. [Give entries their own pages]($docs.entry-pages) has the steps, and [Translate addresses]($docs.translate-addresses) shows how the paths fit together per locale.

## The end of an entry

Use `showUntil` to end entries by date. [Show entries for a time only]($docs.timed-entries) has the steps. The rules:

- Without `showUntil`, every entry shows.
- `showUntil: 'until'` (or `{ field: 'until' }`) shows an entry until the date in the field `until` has passed. The field is a `date` or a `daterange`; for a `daterange` the end date (`to`) counts. An empty field never ends. With `{ field: 'weekOf', plusDays: 6 }` it stays six days longer, for example a week from its first day.

A date counts for the whole day, in the time zone of the site. An entry that ended is not in what a page gets: `useGinko` leaves it out, the detail page returns 404, and the sitemap does not name it.

With `thenDelete: true` in `showUntil`, the platform deletes entries that ended when a new entry needs room. A daily job also deletes entries that ended 30 days ago. Deleted entries can be restored for 30 days.

With `plans: { brick: 'lunch', field: 'weekOf' }`, the entries of a collection plan weeks of the single brick `lunch` ahead: `weekOf` (a `date` field of the collection) holds the first day of the week, and a planned week counts as entered for the weekly reminder.

## Order

`order` sets the order of the entries in the bundle:

- `'manual'`: owners arrange the entries by hand on the platform. For files, the number in the file name sets the order.
- `{ field: 'when', dir: 'asc' }` sorts by a field, ascending (`'asc'`) or descending (`'desc'`). A `daterange` field sorts by `from`, then by `to`.

## Tasks

Tasks (`tasks`) are shortcuts in the editor for a frequent chore. A task does not change what is in the data. It sets which fields a staff member sees and may change.

```ts
tasks: [
  { id: 'closedToday', label: 'Closed today', kind: 'edit', fields: ['closedOn', 'closedNote'], prefill: { closedOn: '@today' } },
  { id: 'add', label: 'Add a dish', kind: 'create', fields: ['name', 'price'] },
  { id: 'remove', label: 'Remove a dish', kind: 'remove' },
]
```

- `kind: 'edit'` changes the fields in `fields`. With `pick: true`, the person first picks an entry.
- `kind: 'create'` adds a new entry. With `fields` the task asks for and writes only those fields (plus its `prefill` and fields with a default); every required field without a default must be in `fields` or `prefill`. A field with a default that the task does not list takes only its default value. The release check refuses the slug and a retired field in `fields`. Without `fields` it asks for every field except the slug.
- `kind: 'remove'` deletes an entry.
- `when: { from: 'ask' }` on an `edit` task lets the person choose the day the values start ("Starts on"). Empty means at once; a day saves a [dated change](#dated-changes) of an online entry. Every field of the task must be one a dated change may set. Without `when` (or with `from: 'now'`) the task saves at once.
- `needsApproval: true` makes a staff change through this task go live only after an owner or admin approves it.
- `prefill` fills fields of the brick in the form in advance. The platform resolves the tokens `'@today'`, `'@workWeek'`, and `'@nextWorkWeek'` in the time zone of the site. A token needs a `date` field; any other value is written like the field's value and checked like it, so a `markdown` field takes Markdown text. `'@workWeek'` is the first day of the work week, `'@nextWorkWeek'` the first day of the week after it. The week starts on `week.firstDay` of the site config. After the last workday of the week (`week.workdays`), the work week is already the coming week, so a weekly plan made on Saturday is for the week ahead.
- A date field that holds a week start (the `field` of `plans`, else the field a task presets to `'@workWeek'` or `'@nextWorkWeek'`) takes only the first day of a week. The `edit` task that presets a field to `'@workWeek'` (the weekly task) always covers the current week: the platform refuses another week there, also when a proposal from an earlier week is approved.

Staff members (role `staff`) may only do what matches a task that the owner has granted to them. You can change tasks at any time. They are not part of the data contract.

::callout{type="note"}
Tasks only make sense for platform bricks. The platform never sees bricks with `source: 'files'`, because nobody edits them in the editor.
::

## Dated changes

A dated change sets fields of an entry from a day on: in a file it is `$changes` ([Content from files]($docs.content-from-files#dated-changes)). A page gets the values of today. With `timeline`, it may also read what comes next for the fields named there:

```ts
timeline: { public: ['price'] }
```

Each entry then carries `upcoming`: the changes still ahead that set one of those fields, in the order of their days, with only those fields:

```vue
<template v-for="change in dish.upcoming" :key="change.from">
  <small v-if="change.data.price">from {{ change.from }}: {{ formatMoney(change.data.price, language) }}</small>
</template>
```

In the Studio, a task with `when: { from: 'ask' }` makes such a change ("A new price from 1 November"), and the editor of an online entry can publish its unpublished changes on a day. On that day the platform writes the values into the entry.

No other waiting value leaves the server, so a text that waits for its day stays private, also in a brick whose coming prices are public. `ginko check` refuses a field in `timeline` that a change cannot set: the slug, a field that `publishedOn` or `showUntil` reads, a field of a navigation tree, and on a site with several languages a text.

## Facts in texts

A price, a phone number or opening times often appear in running text too. So they never go stale there, `facts` names the fields of single bricks that a text may quote:

```ts
facts: ['praxis.price', 'praxis.times', 'site.phone']
```

Ginko adds the inline component `fact` for them. The text holds `:fact{name="praxis.price"}`, the Studio shows a chip with the field's name ("Price per session"). The page, the search, the Markdown twin and `llms-full.txt` show the value in effect today (a dated change from its day on), money as "€ 98", a date in long form, multiple choices and one-column lists as a list ("11:00, 12:15 and 13:30"), an email address or phone number (`format: 'email'` or `'tel'`) as a link.

Allowed are text, number (with `unit`), money, date, time, choice, choices and lists with exactly one column. `ginko check` reports a path that does not name such a field of a single brick. In your own code, `useGinkoFact('praxis.price')` reads the same text; a site that shows `fact` differently gives `<GinkoMarkdown>` its own component under `components`.
