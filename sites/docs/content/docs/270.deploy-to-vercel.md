This guide puts a site online on Vercel. At the end, the site answers on its address, pages come from the cache, and search engines index only the production address.

Vercel is the host Ginko is made and tested for. A site with bricks on the platform needs it, or another host with a server. A site whose bricks all come from files can also be a static site: see [Build a static site]($docs.static-site).

## Before you start

- The site is in a Git repository on GitHub, GitLab or Bitbucket.
- `npx ginko check` passes.

## Steps

::steps
#### Set the production address

```ts [ginko.config.ts]
export default defineSite({
  site: 'linde',
  url: 'https://www.linde.example',
  // …
})
```

`url` is the address the site will have. Ginko writes it into the canonical links and the sitemap. Every other address that serves the site, such as a preview on `*.vercel.app`, tells search engines to stay away.

#### Import the repository on Vercel

In the Vercel dashboard, choose "Add New", then "Project", and pick the repository. Vercel detects Nuxt and runs `nuxt build`. Change nothing in the build settings.

#### Set the environment variables

| Variable | When you need it | Value |
| --- | --- | --- |
| `NUXT_APP_SECRET` | The site has share cards (`nuxt-og-image`, in every template). | A random text of at least 32 characters. Without it, every share card answers with an error. |
| `NUXT_PUBLIC_GINKO_PLATFORM` | The site has bricks on the platform and `ginko.config.ts` does not set `platform`. | The address of the platform. |
| `NUXT_GINKO_REVALIDATE_TOKEN` | The site has bricks on the platform. Optional. | The site token from the Studio (Team, "Site token"). With it, a publish shows at once. |

Set each variable for Production and for Preview. A variable that exists only for Preview leaves the production site without it.

A site whose bricks all come from files and that has no share cards needs no variable.

#### Deploy and check

Vercel builds the site on every push. Check the result with `curl`:

```bash
curl -sI https://www.linde.example/about
```

On the first request the page is rendered, on the second it comes from the cache:

```text
HTTP/2 200
x-vercel-cache: HIT
```

#### Add your domain

In the project on Vercel, open "Settings", then "Domains", and add the address from `url`. From then on, search engines may index the site on that address.
::

## What the site does on Vercel

Each line was measured on a deployed site.

| You ask for | The site answers |
| --- | --- |
| a page | `200`, cached and rendered again at most every 60 seconds |
| a page with a trailing slash or capital letters (`/about/`, `/About`) | `301` to the one address of the page |
| an old address from `redirects` or `redirectFrom`, also with a pattern | `301` to the new address |
| an address that does not exist | a real `404` with your error page |
| a page with `.md` at the end | the page as Markdown, for agents |
| any address on a host other than `url` | the same, with `x-robots-tag: noindex`, and `robots.txt` says `Disallow: /` |

## Deploy from the command line

`vercel deploy` uploads the folder and builds it, without a Git import:

```bash
npx vercel deploy
```

::callout{type="warning" title="The first deploy is production"}
The first deployment of a new project becomes its production deployment, also without `--prod`. Vercel says so in the output. Later runs of `vercel deploy` are previews.
::

## A site that is not ready for search engines

A site that runs on its final address before it is finished sets one more variable on that deployment:

```text
NUXT_PUBLIC_GINKO_NOINDEX=true
```

`robots.txt` then blocks everything, and every answer has `x-robots-tag: noindex`. Remove the variable when the site may be found.

## Release before the deploy

A site with bricks on the platform runs `ginko release` in CI before the deploy, and deploys only when the release says so. [Release a schema change]($docs.release-a-schema-change) has the snippet.
