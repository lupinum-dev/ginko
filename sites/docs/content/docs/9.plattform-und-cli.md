## Was Inhaber auf der Plattform tun

Die Plattform ist eine gehostete Web-App. Sie zeigt aus deinen Bausteinen Formulare und speichert die Inhalte. Die Seite holt die Inhalte als Bundle von dort.

- **Anmeldung.** Personen melden sich mit einem Code an, der per E-Mail kommt. Ein Konto entsteht nur mit Einladung.
- **Rollen.** Ein **Inhaber** (`owner`) darf alles auf seiner Seite und lädt Mitarbeiter ein. Ein **Mitarbeiter** (`staff`) darf nur die Aufgaben, die der Inhaber ihm freigibt. Ein **Admin** darf alles auf allen Seiten.
- **Bearbeiten.** Inhaber ändern Einträge in Formularen. Aufgaben aus den Bausteinen sind Kurzwege für häufige Handgriffe. Eine Vorschau zeigt die echte Seite mit den geänderten Inhalten.
- **Sicherheit.** Ändern zwei Personen dasselbe Feld, merkt die Plattform den Konflikt. Eine Änderung lässt sich rückgängig machen. Gelöschte Einträge bleiben 30 Tage wiederherstellbar.
- **Übersetzungen.** Ändert jemand einen Text in der Hauptsprache, gilt die Übersetzung als veraltet. Die Seite zeigt dann den Text der Hauptsprache, bis jemand die Übersetzung bestätigt oder neu schreibt.
- **Sofort neu laden.** Die Seite lädt Inhalte höchstens alle 60 Sekunden neu. Ein Inhaber kann eine Seite sofort neu laden lassen, zum Beispiel um einen Eintrag von der Seite zu nehmen.

Du als Entwickler legst die Bausteine fest. Die Inhaber füllen sie.

## Das CLI

`ginko` ist ein Befehl im Paket `@lupinum/ginko`. Die Befehle laden deine `ginko.config.ts` (Standard: `./ginko.config.ts`). Mit `--config <datei>` nennst du eine andere Datei. Die Meldungen des CLI sind auf Englisch. In einem Projekt startest du es mit `pnpm exec ginko <befehl>` oder aus einem Skript in der `package.json`.

::code-group
```bash [pnpm]
pnpm exec ginko dev
```
```bash [npm]
npx ginko dev
```
```bash [yarn]
yarn ginko dev
```
::

Diese Umgebungsvariablen steuern die Befehle:

- `GINKO_PLATFORM`: die Adresse der Plattform.
- `GINKO_KEY`: ein Push-Schlüssel der Seite, der Form `ginko_<seite>_<32 Zeichen>`. Er hat Bereiche: `release`, `check`, `export` und `pull`. Die Plattform speichert nur seinen Hash.
- `GITHUB_SHA`: der Commit, den ein Release baut. Nur `release` braucht ihn.

### ginko dev

```bash
ginko dev
```

`ginko dev` startet alles lokal: ein lokales Convex-Backend, die Plattform und deine Seite mit `nuxt dev`. Es schickt dein Schema an die lokale Plattform, sofort und nach jeder Änderung der `ginko.config.ts`. Abgelehnte Änderungen erscheinen als Warnung, laufen aber durch. So darfst du lokal frei probieren. Ändert sich eine Datei, die die Konfiguration importiert, musst du `ginko dev` neu starten. Ctrl-C beendet alle Prozesse.

`ginko dev` läuft nur im Ginko-Monorepo, denn es braucht `apps/platform`. Für eine Seite mit nur Datei-Bausteinen reicht `nuxt dev`.

### ginko pull

```bash
ginko pull
```

`ginko pull` kopiert die Inhalte von production in die lokale Plattform. Es führt `export` aus, dann `import`. So testest du mit echten Inhalten. Der Befehl braucht `GINKO_PLATFORM` und `GINKO_KEY` mit dem Bereich `pull` oder `export`. Er läuft nur gegen die lokale Plattform und bricht ab, wenn das Ziel nicht lokal ist. Er ersetzt die Inhalte der Seite lokal.

### ginko check

```bash
ginko check
```

`ginko check` prüft deine Konfiguration gegen production und schreibt nichts. Es zeigt die erlaubten Änderungen, neue Migrationen und die Größe der Inhalte. Es meldet jede Ablehnung mit einem Vorschlag, wie du sie löst. Bei einem Fehler endet es mit Exit-Code 1. Nutze es in der CI bei jedem Pull Request.

`ginko check` prüft auch die Links in deinen Inhalten. Externe Links (`http://…` und `https://…`) fragt es nur, wenn du `links: { external: 'error' }` (oder `'warn'`) setzt. Es fragt jede Adresse einmal an und meldet nur sichere Fälle: 404, 410, einen unbekannten Host oder zwei Zeitüberschreitungen. Antworten wie 403 oder 429 zählen nicht, weil viele Seiten Bots sperren. Gute Ergebnisse merkt sich Ginko sieben Tage in `node_modules/.cache/ginko`. Dieselbe Prüfung läuft bei `nuxt build` und `nuxt generate`, nie im Dev-Modus. Ohne die Option fragt Ginko kein Netzwerk an.

### ginko release

```bash
ginko release
```

`ginko release` bringt Schema und Inhalte nach production. Du führst es in der CI auf `main` aus. Es tut Folgendes:

1. Es prüft, ob `GITHUB_SHA` noch der neueste Commit von `main` ist. Sonst gibt es `{"deploy":false,"reason":"superseded"}` aus und endet mit Exit-Code 0.
2. Es lädt den Stand von production und prüft dein Schema (siehe unten).
3. Es führt Migrationen aus und prüft alle Einträge.
4. Es schreibt alles in einem Schritt. Hat sich production inzwischen geändert, versucht es bis zu fünf Mal erneut.

Bei Erfolg gibt es `{"deploy":true,"schemaRev":…,"contentRev":…}` aus. Deploye die Seite nur, wenn `deploy` den Wert `true` hat. Dasselbe Release mit gleichem Commit zu wiederholen ist sicher.

### ginko export und ginko import

```bash
ginko export --out ginko-export-meine-seite
ginko import ginko-export-meine-seite
```

`ginko export` sichert Schema, alle Einträge (auch gelöschte) und alle Dateien von production in einen Ordner. Der Ordner muss neu oder leer sein. Ohne `--out` heißt er `ginko-export-<seite>-<jjjj-mm-tt>`. Er enthält `export.json` und den Ordner `files/`. `export.json` wird zuletzt geschrieben: Ein Ordner mit dieser Datei ist vollständig. Der Befehl gibt eine JSON-Zeile mit der Zahl der Einträge und Dateien aus. Er braucht einen Schlüssel mit dem Bereich `export` oder `pull`. Führe ihn wöchentlich in der CI aus und lade den Ordner als Artefakt hoch.

`ginko import <ordner>` lädt einen Export in die lokale Plattform. Es ersetzt dort die Einträge der Seite. Personen bleiben erhalten. Es läuft nur lokal und bricht ab, bevor etwas geschrieben wird, wenn das Ziel nicht lokal ist. Damit prüfst du, ob ein Backup sich wiederherstellen lässt.

## Schemas wachsen nur

Ein Schema in production darf nur wachsen. Inhalte gehören Menschen, und ältere Versionen deiner Seite lesen noch das alte Schema. Darum lehnt `ginko check` und `ginko release` Änderungen ab, die Daten oder alten Code brechen könnten. Die Regel: Alles, was nicht ausdrücklich erlaubt ist, wird abgelehnt.

**Erlaubt:**

- neue Bausteine
- neue freiwillige Felder
- neue Pflichtfelder mit `default` oder mit einer Migration, die sie füllt
- neue Optionen in `choice` und `choices`
- höheres `max` und kleineres `min`
- neue Texte: `label`, `hint`, `describe`, `itemLabel`, Option-Labels
- neue Sprachen am Ende von `locales`
- Änderungen an `pages`, `tasks`, `order`, `visible`, `missing` und `autoRemoveExpired`

**Abgelehnt:**

- ein Feld oder Baustein, der fehlt (nicht umbenennen, nicht löschen)
- ein anderer Typ
- ein freiwilliges Feld, das Pflicht wird
- eine entfernte Option
- kleineres `max`, größeres `min`
- geänderte Übersetzbarkeit, `step`, `currency`, `route`, `timezone` oder Hauptsprache
- eine entfernte Sprache
- ein geänderter `default`

Es gibt also **kein Umbenennen** und **keinen Typwechsel**. Willst du ein Feld ersetzen, legst du ein neues an, füllst es mit einer Migration und ziehst das alte zurück:

```ts
export default defineSite({
  // …
  bricks: {
    menu: collection({
      label: 'Speisekarte',
      fields: {
        headline: f.text('Überschrift'),   // bleibt unverändert in fields
        title: f.text('Titel'),            // neues Pflichtfeld
      },
      max: 150,
      order: 'manual',
    }),
  },
  // Das alte Feld zeigt im Bundle weiter den aktuellen Wert von title.
  retired: { 'menu.headline': { from: 'title' } },
  migrations: {
    '2026-11-title-from-headline': {
      brick: 'menu',
      fills: 'title',
      from: (entry) => entry.headline,
    },
  },
})
```

- `retired` zieht ein Feld zurück. Im Editor verschwindet es. Im Bundle bleibt es erhalten, damit ältere Versionen der Seite weiterlaufen. `from` spiegelt den Wert eines anderen Feldes. Mit `value` legst du einen festen Wert fest. Ein freiwilliges Feld braucht keine Angabe (`{}`).
- Eine Migration ist eine reine Funktion. Sie hat keinen Zugriff auf Netzwerk, Uhr oder Zufall. Sie läuft in `ginko release` auf deinem Rechner oder in der CI, nie auf der Plattform. Ihre ID sieht aus wie `2026-11-name`. Eine bekannte Migration darfst du nicht mehr ändern.

::callout{type="warning"}
Ein Schema-Release lässt sich nicht zurücknehmen. Führe vorher `ginko check` aus. Willst du ein Feld wirklich ersetzen, plane die drei Schritte (neues Feld, Migration, altes Feld zurückziehen) in einem Release ein.
::

Bausteine mit `source: 'files'` gehören nicht zum Schema der Plattform. Für sie gilt diese Regel nicht.
