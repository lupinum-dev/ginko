Die Bausteine und Felder deiner Konfiguration sind das Schema der Seite. Die Plattform hält ihre eigene Kopie, weil die Inhalte der Inhaber davon abhängen. Diese Anleitung bringt eine Änderung des Schemas auf die Plattform. Am Ende zeigt das Studio den neuen Baustein oder das neue Feld, und du weißt, warum manche Änderungen abgelehnt werden.

Eine Seite, deren Bausteine alle aus Dateien kommen, hat kein Schema auf der Plattform und braucht nichts davon.

## Bevor du beginnst

Du hast die Adresse der Plattform und einen Schlüssel mit „Publish and back up“. [Einen Baustein auf die Plattform verlegen]($docs.move-a-brick-to-the-platform) zeigt, woher der Schlüssel kommt.

Das CLI liest keine `.env`-Dateien. Setz die Variablen in der Shell oder als Secrets in CI:

```bash
export GINKO_PLATFORM=https://platform.example.com
export GINKO_KEY=ginko_linde_…
```

## Schritte

::steps
#### Vor dem Commit prüfen

```bash
npx ginko check
```

Der Befehl schreibt nichts. Ohne Änderung sagt er:

```text
Site “linde”: schema version 1, content 1.
No schema changes.
OK: A release with this schema would be accepted.
```

Mit einer Änderung nennt er jede einzeln. `+` ist eine erlaubte Änderung:

```text
Allowed changes:
  + New brick “promo”.
```

#### Beheben, was abgelehnt wird

Eine Änderung, die Inhalte oder älteren Code der Seite brechen könnte, wird abgelehnt. Die Meldung sagt, was zu tun ist:

```text
✗ promo.until: Field “promo.until” is missing.
  → Add a new field, fill it with a migration and list the old field under `retired`.
    // Keep “until” in bricks.promo.fields as it is in production; retired, it leaves the Studio.
    retired: { 'promo.until': { drop: true } },
```

Ein Schema wächst nur. Du löschst ein Feld nicht: Du musterst es aus. Du änderst den Typ eines Feldes nicht: Du ergänzt ein neues Feld und füllst es aus dem alten. [Schemas wachsen nur]($docs.schemas-only-grow) hat jede Regel.

#### Committen und pushen

Die Plattform erkennt ein Release an seinem Commit. Committe die Änderung und pushe sie, bevor du freigibst.

Ein zweites Release desselben Commits schreibt nichts und liefert das Ergebnis des ersten. Das macht einen wiederholten CI-Lauf sicher. Es heißt auch: Ein Release aus nicht committeten Änderungen kommt nicht an, wenn dieser Commit schon freigegeben wurde.

#### In CI freigeben

Lass das Release auf deinem Haupt-Branch laufen, vor dem Deploy:

```bash
result=$(npx ginko release)
if [ "$(echo "$result" | jq -r .deploy)" = "true" ]; then
  npx vercel deploy --prod   # oder der Deploy-Befehl deines Hosters
fi
```

Ein erfolgreiches Release gibt eine Zeile aus:

```json
{"ok":true,"deploy":true,"schemaRev":2,"contentRev":2}
```

Deploye nur, wenn `deploy` `true` ist. Liegt schon ein neuerer Commit auf dem Branch, tritt das Release zurück:

```json
{"ok":true,"deploy":false,"reason":"superseded"}
```

#### Das Ergebnis prüfen

Lass `npx ginko check` noch einmal laufen. Es sagt „No schema changes.“ Öffne das Studio: Der neue Baustein oder das neue Feld ist da.
::

## Von Hand freigeben

Außerhalb von CI braucht das Release den Commit. In GitHub Actions liest es `GITHUB_SHA`; von Hand setzt du `GINKO_COMMIT`:

```bash
GINKO_COMMIT=$(git rev-parse HEAD) npx ginko release
```

Der Commit muss der neueste von `main` auf `origin` sein. Für einen anderen Branch setzt du auch `GINKO_BRANCH`. Ohne den Commit bricht der Befehl ab mit `The environment variable GINKO_COMMIT is missing.`

## Ein Pull Request aus einem Fork

GitHub gibt einem Pull Request aus einem Fork keine Secrets. Lass die Prüfung dort ohne den Vergleich laufen:

```bash
npx ginko check --offline
```

Sie prüft die Konfiguration, die Inhaltsdateien und die Links und gibt `Skipped the comparison with production (--offline).` aus.
