A Markdown field in Ginko accepts a defined set of parts, not everything Markdown can write. A text with another part is refused: in a file by the build, on the platform by the editor. This page explains the rules and their reasons.

## Why there are rules

- **Owners write the text.** A person who is not a developer writes into a field on the platform. Nothing they type or paste may break the page or run code.
- **The design is yours.** A heading in a card with a fixed height, or a table in a one-line teaser, breaks a layout. The developer says what fits in each place.
- **The text has several readers.** The same text feeds the page, the search, the Markdown version for agents and the share card. A defined set of parts works in all of them.

The site gets a Markdown text as a tree of known parts, never as HTML. `<GinkoMarkdown>` draws that tree with Vue components. Nothing uses `v-html`, and no parser runs in the browser.

## Profiles

Each Markdown field has a profile. It says how much the text may contain:

```ts
teaser: f.markdown('Teaser', { profile: 'inline' }),
body: f.markdown('Text', { profile: 'page' }),
```

| Profile | Allows | Made for |
| --- | --- | --- |
| `inline` | One paragraph with bold, italic, strikethrough, code and links | A teaser, a caption, one line in a card |
| `basic` | Also headings h2 to h4, lists, task lists, quotes, dividers and footnotes | A text in a section, such as a job description |
| `rich` | Also tables, images, code blocks, math and mermaid diagrams | An article. The default. |
| `page` | Also h1, h5, h6 and components such as `::callout` | A whole page, such as a docs page |

Choose the smallest profile that holds the content. A text that goes over it gets a clear message, which lists what the profile allows:

```text
content/start.md (body.en): “body”: “callout” is not allowed here (paragraphs, headings, lists (also with checkboxes), quotes, notices and footnotes).
```

`inline`, `basic` and `rich` have no h1. The title of the page is the h1, so a text starts at h2.

## Components

Only the profile `page` accepts components, and only the ones the site registers in `components` of `ginko.config.ts`. Each component declares its properties, so a text can use only what the component knows:

```text
There is no component “callot”.
Component “callout”: There is no property “colour”.
Component “pricing”: property “price” is missing.
```

This check is the reason a component stays safe to change. When you rename a property, `ginko check` finds every text that still uses the old name. On the platform, a release checks every stored text again, so a component that a text still uses cannot go.

[Set up the components]($docs.set-up-components) registers the ready-made ones. [Add your own component]($docs.add-your-own-component) adds one.

## What is always refused

These tags run code, load other content or send data. No profile and no registry allows them:

`script`, `style`, `iframe`, `frame`, `frameset`, `object`, `applet`, `link`, `meta`, `base`, `form`, `button`, `textarea`, `select`, `option`, `template`, `noscript`, `svg`, `portal`, `slot`

```text
content/start.md (body.en): “body”: “iframe” is not allowed.
```

`embed` is refused too, with one exception: a site that registers the component `embed` of `@lupinum/ginko-components` gets that component. It shows a map or a player from a known provider, and loads nothing before the visitor presses a button. See [Media components]($docs.components-media#embed).

Need a form or an iframe in a text? Write a component for it and register it. Then the code is yours and reviewed, and the text only names it.

## Attributes

A part of a text can carry attributes: `**new**{lang="en"}`. Ginko keeps a short list.

| Attribute | On | Purpose |
| --- | --- | --- |
| `title`, `lang`, `dir`, `aria-*` | every element | Meaning and accessibility |
| `aspect`, `fit` | an image | Crops the picture to a frame: `{aspect="4:3" fit="contain"}` |
| the declared properties | a component | What the registry lists for it |

Every other attribute is refused:

```text
content/start.md (body.en): “body”: The property “style” is not allowed.
```

Two cases surprise people:

- **`style`.** A text with its own colours and sizes goes against the design of the site, and CSS in content is a way to hide or move parts of a page.
- **`class` and `data-*`.** Both are hooks of the CSS of your site. A text that could set `class="hidden"` could switch parts of the layout.

For a part with its own look, write a component. Its properties are the choices an author has.

## Links

A link or an image address must be one of these:

| Form | Example |
| --- | --- |
| A web address | `https://example.com` |
| An email or a phone number | `mailto:hello@example.com`, `tel:+43 1 234567` |
| A path on the site | `/menu` |
| A heading on the page | `#prices` |
| A link to an entry or a page | `$news.opening`, `$pages.menu` |

Everything else is not a link:

- `[text](javascript:…)` and `[text](data:…)` stay text. The page shows the characters as they were typed, and nothing can be clicked.
- An address that starts with `//` leads to another site without saying so. The build refuses it:

```text
content/start.md (body.en): “body”: Link is not allowed (only http, https, mailto, tel or /path).
```

Prefer the last form. Ginko turns `$news.opening` into the address of that entry in the language of the page, and the link check finds it when the entry is gone. [Link between pages]($docs.link-between-pages) has the steps.

## Raw HTML

Ginko's Markdown has no raw HTML. A tag in a text is text: `<div class="box">` shows on the page as these characters, and a `<script>` in a text never runs. For structure beyond Markdown, there are components.
