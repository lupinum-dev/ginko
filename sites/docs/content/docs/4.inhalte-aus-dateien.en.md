## What files are for

A brick with `source: 'files'` reads its entries from Markdown files in the repo. Use it for texts that developers maintain: docs, a blog, legal pages. These docs use it themselves.

The site reads file content the same way as platform content: with `useGinko` and `useGinkoEntry`. At build time, Ginko reads the files and builds the same bundle as the platform does. Visibility, order, addresses, locales, and fallback work unchanged.

A brick has exactly one source. The platform never sees file bricks. A site whose bricks all come from files never asks the platform and needs no platform address.

## Set it up

You need the package `@lupinum/ginko-content` in the dependencies of the site. If it is missing, the build stops with a message that says what to install.

You describe the brick like any other and set `source: 'files'`. The text of the file fills a field of type `f.markdown`:

```ts
import { collection, defineSite, f } from '@lupinum/ginko'

export default defineSite({
  site: 'ginko-docs',
  name: 'Ginko',
  url: 'https://ginko-docs.vercel.app',
  timezone: 'Europe/Vienna',
  locales: ['de', 'en'],
  currency: 'EUR',
  pages: { home: { de: '/', en: '/en' } },
  bricks: {
    docs: collection({
      label: 'Docs',
      source: 'files',
      max: 500,
      order: 'manual',
      route: { de: '/doku/[slug]', en: '/en/docs/[slug]' },
      fields: {
        title: f.text('Title'),
        description: f.longtext('Description', { optional: true }),
        slug: f.slug('Address', { from: 'title' }),
        body: f.markdown('Text'),
      },
    }),
  },
})
```

These rules apply to file bricks:

- A file brick has at most one Markdown field: the text of the file. It is not allowed in a list there.
- `profile` sets what the text may contain: `inline`, `basic`, `rich` (default) or `page` (also components such as `::callout`). Raw HTML stays text.
- A slug field must be called `slug`.

## File layout

The files live in the folder `content/` next to `nuxt.config.ts`:

```text
content/
  docs/                       # collection "docs"
    1.einstieg.md             # main locale. The number is the order.
    1.einstieg.en.md          # translation: same name plus .en
    2.bausteine.md
  rechtliches.md              # single "rechtliches"
  rechtliches.en.md
```

- A **collection** has a folder `content/<brick>/`. Each file is one entry.
- A **single** is one file `content/<brick>.md`.
- The file of the main locale has no locale code. A translation has the same name and ends in `.<locale>.md`, for example `.en.md`.
- The number before the name is the order. Files without a number come after them, sorted by name. The number sets the order for `order: 'manual'`.
- The **id** of an entry is the path without number, locale, and extension, for example `docs/einstieg`.
- Images and files live in the folder `public/`.

A translation without a file in the main locale is an error.

## Frontmatter

The **frontmatter** is a YAML block at the start of the file. It fills the fields of the brick in a simple form. The text below the frontmatter fills the Markdown field. The Markdown field itself never appears in the frontmatter.

```markdown
---
title: Getting started
description: What Ginko is.
---

## What Ginko is

Ginko connects a Nuxt site with its content.
```

This is how you write each type:

| Type | Form in the frontmatter |
| --- | --- |
| `text`, `longtext` | Text. The locale comes from the file name. |
| `number`, `boolean` | `42` or `true` |
| `money` | Amount as a number: `12.50` |
| `date`, `time` | `2026-10-12` and `18:30` |
| `daterange` | `from: 2026-10-12` and `to: 2026-10-14`, indented under the field name |
| `choice` | the value of the option |
| `choices`, `list` | a YAML list. A list row is an object with the columns. |
| `image` | `src` (path under `public/`) and `alt`, indented under the field name |
| `file` | path under `public/` |

These rules apply to translations:

- A translation file contains only fields that are translatable. A number field in the file `*.en.md` is an error.
- For an image, the translation gives only `alt`, not `src`.
- A list in the translation must not have more rows than the list in the main locale. Ginko matches rows by their position.
- Translations are always current. There is no "outdated". If a translation is missing, the fallback of the brick applies (`missing`).

**Slug.** Without a value in the frontmatter, Ginko takes the file name without the number, for example `einstieg` for `1.einstieg.md`. A translation may set its own slug with `slug:`. Two entries with the same slug in one locale are an error.

## Show Markdown

`<GinkoMarkdown>` shows the value of an `f.markdown` field. The Ginko module registers the component in every site.

```vue
<script setup lang="ts">
import Callout from './Callout.vue'

const route = useRoute()
const doc = useGinkoEntry('docs', String(route.params.slug))
</script>

<template>
  <article>
    <h1>{{ doc.data.title }}</h1>
    <GinkoMarkdown :value="doc.data.body" :components="{ callout: Callout }" />
  </article>
</template>
```

The parser runs at build time. There is no parser at runtime. Ginko highlights code in code blocks with Shiki. Code sits on a dark panel; its colours come from the `catppuccin-mocha` theme. Ginko knows these languages: `typescript`, `javascript`, `json`, `vue`, `bash`, `markdown`, `yaml`, `html`, and `css`. Other languages appear without color.

**Components.** In Markdown, you write a component as a block with two colons:

```markdown
::callout{type="warning"}
An error in a file stops the build.
::
```

Ginko stores the block as an element `callout`. The site decides with `:components` which Vue component belongs to it. The package `@lupinum/ginko-components` brings ready-made components such as `callout`, `kbd` and `badge`. You register your own like this:

```vue
<!-- Callout.vue -->
<script setup lang="ts">
defineProps<{ type?: 'note' | 'warning' }>()
</script>

<template>
  <aside class="callout" :data-type="type ?? 'note'"><slot /></aside>
</template>
```

**Table of contents.** In the bundle of a page, a Markdown field holds only a reference and the table of contents `toc`. `<GinkoMarkdown>` fetches the text of the current page. So the page carries only the texts that it shows. `toc` holds the headings of levels 2 and 3. Each link has `id` and `text`:

```ts
const toc = computed(() => (doc.value.data.body.toc as { links?: { id: string; text: string }[] } | undefined)?.links ?? [])
```

## Images

An image can sit next to the Markdown file and be referenced with a relative path. Ginko reads the size from the file, stores the image under a name from its content (`/_ginko/img/<hash>.jpg`, cached for a year) and sets `width` and `height`, so the page does not shift while loading.

```md
![The kitchen in morning light](./kueche.jpg)
```

![The kitchen in morning light](./kueche.jpg)

The path must stay inside `content/`; if the file is missing, the build fails with the file and path. Paths starting with `/` look in `public/` (only the size is added); `https://` images stay unchanged. Image fields render with `<GinkoImage :image="entry.data.hero" />`, with size and `loading="lazy"` (`eager` for the first image on the page).

## Errors

An error in a file stops the build. The message starts with `[ginko] Fehler in content/` and names the file and the field. These are examples:

- a frontmatter key that the brick does not know
- a locale code in the file name that the site does not have
- a translation without a file in the main locale
- two entries with the same slug in one locale
- an image or file that is missing under `public/`
- a value that the rules of the field reject, for example a title that is too long
- text below the frontmatter although the brick has no Markdown field

::callout{type="warning"}
In dev mode, an error does not stop the server. Ginko writes the error to the log and leaves the file out. So check the log when a page is missing.
::
