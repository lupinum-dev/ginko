This guide translates text on the server. At the end, an API route answers in the language of the request, and a server component renders in the language of its page.

## Before you start

The app has `@lupinum/ginko-i18n` set up, see [i18n quick start]($docs.i18n-quick-start).

## Translate in a server route

::steps
#### Add the message

```json [i18n/en.json]
{ "contact": { "sent": "Thank you. We answer within two days." } }
```

```json [i18n/de.json]
{ "contact": { "sent": "Danke. Wir antworten in zwei Tagen." } }
```

#### Call getI18n

`getI18n` needs no import in a server route:

```ts [server/api/contact.post.ts]
export default defineEventHandler((event) => {
  const { t, locale } = getI18n(event)
  return { locale, message: t('contact.sent') }
})
```

It returns `t`, `parts`, `has` and `format` as `useI18n` does, with the same typed keys. Here `locale` and `language` are plain strings.
::

### Check that it works

```bash
curl -X POST http://localhost:3000/api/contact
curl -X POST -H "Accept-Language: de" http://localhost:3000/api/contact
curl -X POST -H "Cookie: ginko_locale=de" -H "Accept-Language: en" http://localhost:3000/api/contact
```

The first answers in English, the default language. The second and the third answer in German:

```json
{ "locale": "de", "message": "Danke. Wir antworten in zwei Tagen." }
```

### Where the language of a request comes from

| Request | Language |
| --- | --- |
| A page such as `/de/ueber-uns` | The address. |
| A path without a prefix, such as `/api/**` | The cookie `ginko_locale`, then `Accept-Language`, then the default language. |
| A page in a user-locale zone | The same as `/api/**`. |

To answer in the language of the page that called the route, send it along: `$fetch('/api/contact', { method: 'POST', headers: { 'Accept-Language': locale.value } })`.

::callout{type="warning" title="Do not cache these answers"}
An answer whose language comes from a header or a cookie must not be cached with `isr`, `swr` or `cache`. Vercel ISR and Nitro SWR ignore `Vary`, so every visitor would get the language of the first one. The build warns when a route rule does this.
::

## Translate in a server component

Nuxt does not give the address of the page to a server component. So the component cannot see the language. Pass it as a prop:

```vue [app/components/OpenCard.server.vue]
<script setup lang="ts">
defineProps<{ locale?: string }>()

const { t } = useI18n()
</script>

<template>
  <p>{{ t('nav.about') }}</p>
</template>
```

```vue [app/pages/privacy.vue]
<script setup lang="ts">
const { locale } = useI18n()
</script>

<template>
  <main>
    <OpenCard :locale="locale" />
  </main>
</template>
```

Server components need `experimental: { componentIslands: true }` in `nuxt.config.ts`.

### Check that it works

Open `/de/privacy`. The component shows "Über uns". Without the prop it shows "About us", and the dev server warns:

```text
[ginko-i18n] Island "OpenCard" has no locale and renders in en. Fix: pass :locale="locale" (from useI18n()) to the server component.
```

## Translate outside Nuxt

The translator also runs without Nuxt, for example in a Convex function, an email or a script. [i18n reference]($docs.i18n-reference#without-nuxt) shows `defineCatalog` and `createTranslator`.
