This guide connects a Ginko website to your platform. At the end, the Studio lists the areas of the website, the website loads its content from the platform, and the owners can sign in.

## Before you start

- Your platform is online, and you are signed in as admin. See [Put the platform online]($docs.put-the-platform-online).
- The website is a Ginko site in a Git repository, and at least one brick has no `source: 'files'`. [Move a brick to the platform]($docs.move-a-brick-to-the-platform) shows that change. If the website has content in files that should move too, follow [A website with content in files](#a-website-with-content-in-files) instead.

## Steps

::steps
#### Create the site in the Studio

Only an admin creates sites. Choose "New site", then fill in the name, the website address and the identifier. The identifier is the same value as `site` in the `ginko.config.ts` of the website, and it cannot be changed later. Choose "Create site".

The Content page of the new site shows "Connect the website", with the steps and the values of this site.

#### Get a publishing key

In the folder of the website, run `ginko connect` with the address of your Studio:

```bash
npx ginko connect https://cms.example.com
```

The terminal shows a code, and the browser opens the page `/connect` of your Studio:

```text
Open https://cms.example.com/connect and enter this code: <code>
```

In the Studio, type the code, choose the site and choose "Connect". Owners and admins of a site can do this. The code is valid for 10 minutes. The terminal then says:

```text
Connected to the site “linde”.
```

::callout{type="warning"}
Confirm only a code that you started yourself, in your own terminal. Whoever started the request gets the key.
::

The key can publish the content structure of the site and back up its content, like a "Publish and back up" key. You can revoke it on the Team page.

Where the key goes:

- If the folder is a GitHub repository and the [GitHub CLI](https://cli.github.com) `gh` is installed, the command asks whether to store the key as the secret `GINKO_KEY` and the address as the variable `GINKO_PLATFORM` of that repository. After a yes, it stores both.
- Otherwise, it shows the key once. Store it as the secret `GINKO_KEY` of your CI.

The other way: on the Team page of the site, under "Publishing keys", choose "New key", give it a name, choose "Publish and back up" and create it. The Studio shows the key once.

#### Set the identifier and the platform address

```ts [ginko.config.ts]
export default defineSite({
  site: 'linde',
  platform: 'https://cms.example.com',
  // …
})
```

`site` is the identifier from the Studio. If it is missing or different, `ginko connect` prints the line to set. `platform` is the address of your Studio, the one people open to sign in. The website and the `ginko` CLI need only this one address: the CLI reads from the Studio where the backend answers.

#### Run the first release

Commit the change and push it to `main`. Then run the release in the project of the website, with your key in place of the dots:

```bash
GINKO_PLATFORM=https://cms.example.com GINKO_KEY=… GINKO_COMMIT=$(git rev-parse HEAD) npx ginko release
```

After the release, the Content page lists the areas of the website. [Release a schema change]($docs.release-a-schema-change) shows how later releases run in CI.

#### Give the website a site token

This step is optional. Without a token, a publish reaches the website within 60 seconds. With it, the website shows a publish at once, and "Update website now" works.

On the Team page, under "Site token", choose "Create token". Set the token on the host of the website as `NUXT_GINKO_REVALIDATE_TOKEN`, for Production and Preview, and deploy again. [Environment variables]($docs.environment-variables) explains the token.

#### Invite the owners

On the Team page of the site, choose "Invite", enter the email address and choose the role:

- **Owner**: may change everything, manage the team and delete the site. Only an admin invites owners.
- **Staff**: may change only what the owner ticks under "Rights". Owners and admins invite staff.

Choose "Send invitation". The person gets a mail with a link and signs in with a code.
::

## A website with content in files

A Ginko website that keeps its content in files (`content/`) can move it into a site of your platform. In this order, the live website keeps showing its files until the content is on the platform.

::steps
#### Create the site and get a key

Create the site with "New site", and get a key with `ginko connect`, as in the steps above.

#### Save the content of the files

In the folder of the website:

```bash
npx ginko files-export
```

It writes the schema and the `content/` files, with the images they use, to the folder `ginko-export-<site>-files`. Drafts and entries planned for later stay out; the command names them, and you add them in the Studio.

#### Release the schema from a branch

On a new branch, for example `move-to-platform`, remove `source: 'files'` from every brick in `ginko.config.ts`. Commit, and push the branch, not `main`. Then release it by hand, with `GINKO_PLATFORM` and `GINKO_KEY` set:

```bash
GINKO_BRANCH=move-to-platform GINKO_COMMIT=$(git rev-parse HEAD) npx ginko release
```

The release sends the schema. The import in the next step does not.

#### Import the content

In the folder of the platform project:

```bash
npx ginko-platform import <path to the export folder> --site linde --prod
```

`--prod` imports into the production deployment that `ginko-platform.json` names. Without it, the command imports into the local backend of `npm run dev`; create the site there first, too. The import takes only a site without content.

#### Merge the branch

Merge the branch into `main`. Its release and deploy now find the content on the platform.
::

Why a branch: `ginko release` releases only the newest commit of `GINKO_BRANCH` (default `main`), and the website deploys from `main`. So the schema reaches the platform while the live website still reads its files. Between the release from the branch and the merge, a release from `main` fails, because it would remove the moved bricks from the platform. Keep that time short.
