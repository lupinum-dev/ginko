## One version for all packages

Ginko is seven packages on npm. They always release together, with one version:

`@lupinum/ginko`, `@lupinum/ginko-i18n`, `@lupinum/ginko-content`, `@lupinum/ginko-components`, `@lupinum/ginko-docs`, `@lupinum/ginko-preset-gastro` and `create-ginko`

So a site has one Ginko version. Keep every Ginko package of a site on the same version: packages of different versions are not tested together.

## What a release may change

Ginko is before 1.0. Until then:

| Release | Example | What it may contain |
| --- | --- | --- |
| Patch | 0.17.0 to 0.17.1 | Fixes. A patch never needs a change in your site. |
| Minor | 0.17.1 to 0.18.0 | New features, and changes that need a change in your site. The changelog names each of these and says what to do. |

Some parts have a stronger promise. The addresses and headers on [What a site serves]($docs.site-output#addresses-and-headers) change their name or meaning only in a minor release, and the changelog names the change.

Everything a page calls internal has no promise: `@lupinum/ginko/internal`, the addresses under `/__ginko/` that are not listed as stable, and the CSS classes of the kits.

## What Ginko needs

| | Version |
| --- | --- |
| Node | 22.18 or later, 24 or 26 |
| Nuxt | 4.6 or later |
| Vue | 3.5 or later |

## The changelog

The [changelog](/changelog) has one entry per release. An entry groups its notes:

| Group | Meaning |
| --- | --- |
| Added | Something new. Nothing to do. |
| Changed | Something works in another way. Read these before an upgrade. |
| Fixed | An error is gone. |
| Removed | Something is gone. Read these before an upgrade. |

A note ends with a link to its pull request on GitHub, where the change and its reason are.

## Where the entries come from

Every pull request that changes a package adds one line for the changelog: a sentence that starts with Add, Change, Fix or Remove and says what changes for you. A release collects these lines into the file `CHANGELOG.md` of each package.

The build of these docs reads the seven files, joins the notes of one version and writes the entry. So a new release is in the changelog after the next deploy of the docs, and the changelog cannot miss a release.

The same notes are in each package on npm, in `node_modules/@lupinum/ginko/CHANGELOG.md`, and in the [releases on GitHub](https://github.com/lupinum-dev/ginko/releases).
