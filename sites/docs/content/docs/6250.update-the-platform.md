This guide brings a new version of Ginko to your platform. At the end, the Studio and the backend run the new version, and the data migrations it brings have run.

## Steps

::steps
#### Read the changelog

The [changelog](/changelog) lists each version. Look for two things: a breaking change, and a data migration of the platform. Before an update that brings a migration, back up first (see below).

#### Raise the three versions

In the `package.json` of the platform project, set `@lupinum/ginko`, `@lupinum/ginko-server` and `@lupinum/ginko-studio` to the new version. All three always have the same version.

```json [package.json]
"@lupinum/ginko": "0.18.0",
"@lupinum/ginko-server": "0.18.0",
"@lupinum/ginko-studio": "0.18.0",
```

Then install:

```bash
npm install
```

Try the new version on your computer with `npm run dev` if you like. The local backend runs the migrations too.

#### Deploy

```bash
vercel deploy --prod
```

If the Vercel project is connected to Git, push to the production branch instead.

The build deploys the backend first, then starts its data migrations, then builds the Studio. If the backend deploy fails, the build fails and the previous version stays online.

#### Read the migrations line

The build log has one line about the migrations, for example:

```text
Migrations: all 5 done.
```

```text
Migrations: started <name> (2 pending). Progress: npx convex run ops:status
```

The migrations run in the background, one after the other. Nobody runs them by hand. To follow them, run `ops:status` on the production deployment. Its reference is `convex.deployment` in `ginko-platform.json`:

```bash
npx convex run ops:status '{}' --deployment <deployment>
```

The answer has `migrations`: how many are done, which are pending, the running one, and a stopped one with its error. A stopped migration starts again from where it stopped with the next deploy. If the log says `Warning: the data migrations could not be started. The next deploy tries again; see ops:status.`, the new backend is online, and the next deploy starts the migrations.

If the log says `Warning: CONVEX_DEPLOY_KEY may deploy but may not start the data migrations.`, the deploy key lacks a right. A key from `ginko-platform setup` has it. A key that you made in the Convex dashboard has only the rights you ticked there. Make a new deploy key with the rights `deployment:deploy` and `deployment:functions:runInternalMutations`, set it as `CONVEX_DEPLOY_KEY` in the Vercel project, and deploy again. Or start the migrations once with your own login:

```bash
npx convex run migrations:runPending '{}' --deployment <deployment>
```
::

## Back up before an update with a migration

A deploy starts the migrations by itself, so a backup after the deploy is too late. Back up the whole backend first, in one of two ways:

- In the Convex dashboard, open the production deployment and create a backup there.
- With the Convex CLI, to a ZIP file with all data and all stored files:

```bash
npx convex export --path backup.zip --include-file-storage --deployment <deployment>
```

Owners can also back up the content of one site: the Studio's Team page has "Backup", and `ginko export` makes the same copy from the command line. See [Export and back up]($docs.export-and-backup).

## The platform first, then the websites

The platform must run the same or a newer minor version than the `@lupinum/ginko` of each website. So update the platform first, then the websites.

If a website is newer, `ginko release` and `ginko check` print a sentence like this one, and continue:

```text
This platform runs Ginko 0.17.1; the site uses 0.18.0. Update the platform first if the release is rejected.
```

A release that uses something the older platform does not know is rejected.

## Preview builds

Setup sets the values of the Studio for the Production environment of Vercel only. A preview build, for example of another branch, has none of them, and its build stops. Turn off preview builds in the Vercel project, or give them their own values that point at a separate Convex project. Never point a preview at the production deployment.
