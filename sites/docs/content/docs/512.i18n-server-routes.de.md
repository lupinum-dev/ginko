Diese Anleitung übersetzt Texte auf dem Server. Am Ende antwortet eine API-Route in der Sprache der Anfrage, und eine Server-Komponente erscheint in der Sprache ihrer Seite.

## Bevor du beginnst

In der App ist `@lupinum/ginko-i18n` eingerichtet, siehe [i18n-Schnellstart]($docs.i18n-quick-start).

## In einer Server-Route übersetzen

::steps
#### Den Text anlegen

```json [i18n/en.json]
{ "contact": { "sent": "Thank you. We answer within two days." } }
```

```json [i18n/de.json]
{ "contact": { "sent": "Danke. Wir antworten in zwei Tagen." } }
```

#### getI18n aufrufen

`getI18n` braucht in einer Server-Route keinen Import:

```ts [server/api/contact.post.ts]
export default defineEventHandler((event) => {
  const { t, locale } = getI18n(event)
  return { locale, message: t('contact.sent') }
})
```

Es liefert `t`, `parts`, `has` und `format` wie `useI18n`, mit denselben typisierten Schlüsseln. Hier sind `locale` und `language` einfache Strings.
::

### Prüfe, ob es funktioniert

```bash
curl -X POST http://localhost:3000/api/contact
curl -X POST -H "Accept-Language: de" http://localhost:3000/api/contact
curl -X POST -H "Cookie: ginko_locale=de" -H "Accept-Language: en" http://localhost:3000/api/contact
```

Die erste Anfrage bekommt eine Antwort auf Englisch, der Hauptsprache. Die zweite und die dritte bekommen eine Antwort auf Deutsch:

```json
{ "locale": "de", "message": "Danke. Wir antworten in zwei Tagen." }
```

### Woher die Sprache einer Anfrage kommt

| Anfrage | Sprache |
| --- | --- |
| Eine Seite wie `/de/ueber-uns` | Die Adresse. |
| Ein Pfad ohne Präfix, wie `/api/**` | Das Cookie `ginko_locale`, dann `Accept-Language`, dann die Hauptsprache. |
| Eine Seite in einer Zone mit Nutzersprache | Wie bei `/api/**`. |

Soll die Route in der Sprache der Seite antworten, die sie aufruft, schick die Sprache mit: `$fetch('/api/contact', { method: 'POST', headers: { 'Accept-Language': locale.value } })`.

::callout{type="warning" title="Diese Antworten nicht cachen"}
Eine Antwort, deren Sprache aus einem Header oder einem Cookie kommt, darf nicht mit `isr`, `swr` oder `cache` gecacht werden. Vercel ISR und Nitro SWR ignorieren `Vary`, also bekäme jeder Besucher die Sprache des ersten. Der Build warnt, wenn eine Route-Regel das tut.
::

## In einer Server-Komponente übersetzen

Nuxt gibt einer Server-Komponente die Adresse der Seite nicht. Die Komponente sieht also die Sprache nicht. Gib sie als Prop mit:

```vue [app/components/OpenCard.server.vue]
<script setup lang="ts">
defineProps<{ locale?: string }>()

const { t } = useI18n()
</script>

<template>
  <p>{{ t('nav.about') }}</p>
</template>
```

```vue [app/pages/privacy.vue]
<script setup lang="ts">
const { locale } = useI18n()
</script>

<template>
  <main>
    <OpenCard :locale="locale" />
  </main>
</template>
```

Server-Komponenten brauchen `experimental: { componentIslands: true }` in `nuxt.config.ts`.

### Prüfe, ob es funktioniert

Öffne `/de/privacy`. Die Komponente zeigt „Über uns“. Ohne die Prop zeigt sie „About us“, und der Dev-Server warnt:

```text
[ginko-i18n] Island "OpenCard" has no locale and renders in en. Fix: pass :locale="locale" (from useI18n()) to the server component.
```

## Außerhalb von Nuxt übersetzen

Der Übersetzer läuft auch ohne Nuxt, zum Beispiel in einer Convex-Funktion, einer E-Mail oder einem Skript. Die [i18n-Referenz]($docs.i18n-reference#ohne-nuxt) zeigt `defineCatalog` und `createTranslator`.
