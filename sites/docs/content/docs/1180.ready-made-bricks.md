This guide adds bricks that most sites need without writing their fields: legal texts, a team, a blog, job ads, questions and answers, downloads. At the end, the site reads a finished brick, and its entries carry the data search engines look for.

The bricks come with `@lupinum/ginko`. You install nothing.

## Steps

::steps
#### Pick the bricks

| Function | Kind | Content |
| --- | --- | --- |
| `site()` | single | legal name, address, email, phone, registration and VAT number |
| `legal()` | collection | one legal text per entry: privacy, imprint, terms and others |
| `people()` | collection | name, role, short bio, email, phone, photo |
| `posts()`, `authors()` | collections | posts with date, authors and tags |
| `changelog()` | collection | one entry per version |
| `jobs()` | collection | job ads that leave the site after their last day |
| `faq()` | collection | question and answer |
| `downloads()` | collection | title, summary, date and a PDF |

#### Add them to the config

Each function returns a brick. Put it under the key you want:

```ts [ginko.config.ts]
import { defineSite } from '@lupinum/ginko'
import { faq, jobs, legal, site } from '@lupinum/ginko/patterns'

export default defineSite({
  // name, url, timeZone, locales: ['en', 'de'], currency, pages
  // The page of one legal text and of one job. Ginko adds `/de` for German.
  entries: { legal: '/[slug]', jobs: '/jobs/[slug]' },
  bricks: {
    site: site(),
    legal: legal(),
    jobs: jobs(),
    faq: faq(),
  },
})
```

- The content is in files. To let the owner edit a brick on the platform instead, name it in `studio.bricks`.
- An entry of `legal()`, `posts()` or `jobs()` gets its own page when its brick has a line in `entries`.
- `label` replaces the name of the brick in the Studio. To change anything else, wrap the pattern in `extend` of `@lupinum/ginko`.

#### Write an entry

The fields of each brick are fixed. For `faq()` they are `question` and `answer`:

```markdown [content/faq/1.hours.md]
---
question: When are you open?
answer: Monday to Friday, 9 to 17.
---
```

Your editor shows the fields of a brick when you read it in a page: `item.data.` lists them.

#### Read the brick in a page

A ready-made brick reads like your own:

```vue
<script setup lang="ts">
const faq = useGinko('faq')
</script>

<template>
  <dl>
    <template v-for="item in faq.items" :key="item.id">
      <dt>{{ item.data.question }}</dt>
      <dd>{{ item.data.answer }}</dd>
    </template>
  </dl>
</template>
```

The layout is yours. The bricks bring content types, not components.

#### Check the result

Run `npx ginko check`, then open the page. The question and the answer from the file show.
::

## What a ready-made brick brings

- **Fields and their labels** for the Studio, in German, English, Spanish and French.
- **Tasks for owners** on the platform, such as "Add a question".
- **Data for search engines.** Most bricks have a helper that writes the schema.org data of their entries, such as `faqJsonLd` and `jobJsonLd`. [Composables and components]($docs.reading-content#ready-made-bricks-and-helpers) lists them.
