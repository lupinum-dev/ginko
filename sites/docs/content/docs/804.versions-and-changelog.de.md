## Eine Version für alle Pakete

Ginko besteht aus sieben Paketen auf npm. Sie erscheinen immer zusammen, mit einer Version:

`@lupinum/ginko`, `@lupinum/ginko-i18n`, `@lupinum/ginko-content`, `@lupinum/ginko-components`, `@lupinum/ginko-docs`, `@lupinum/ginko-preset-gastro` und `create-ginko`

Eine Website hat also eine Ginko-Version. Halte jedes Ginko-Paket einer Website auf derselben Version: Pakete verschiedener Versionen sind nicht zusammen getestet.

## Was ein Release ändern darf

Ginko ist vor 1.0. Bis dahin gilt:

| Release | Beispiel | Was es enthalten darf |
| --- | --- | --- |
| Patch | 0.17.0 auf 0.17.1 | Fixes. Ein Patch braucht nie eine Änderung an deiner Website. |
| Minor | 0.17.1 auf 0.18.0 | Neue Funktionen und Änderungen, die eine Anpassung deiner Website brauchen. Das Changelog nennt jede davon und sagt, was zu tun ist. |

Manche Teile haben ein stärkeres Versprechen. Die Adressen und Header auf [Was eine Seite ausliefert]($docs.site-output#adressen-und-header) ändern ihren Namen oder ihre Bedeutung nur in einem Minor-Release, und das Changelog nennt die Änderung.

Alles, was eine Seite intern nennt, hat kein Versprechen: `@lupinum/ginko/internal`, die Adressen unter `/__ginko/`, die nicht als stabil aufgeführt sind, und die CSS-Klassen der Kits.

## Was Ginko braucht

| | Version |
| --- | --- |
| Node | 22.18 oder neuer, 24 oder 26 |
| Nuxt | 4.6 oder neuer |
| Vue | 3.5 oder neuer |

## Das Changelog

Das [Changelog](/changelog) hat einen Eintrag pro Release. Ein Eintrag gruppiert seine Notizen:

| Gruppe | Bedeutung |
| --- | --- |
| Added | Etwas Neues. Nichts zu tun. |
| Changed | Etwas funktioniert anders. Lies diese vor einem Update. |
| Fixed | Ein Fehler ist behoben. |
| Removed | Etwas ist weg. Lies diese vor einem Update. |

Eine Notiz endet mit einem Link zu ihrem Pull Request auf GitHub, wo die Änderung und ihr Grund stehen.

## Woher die Einträge kommen

Jeder Pull Request, der ein Paket ändert, ergänzt eine Zeile für das Changelog: einen Satz, der mit Add, Change, Fix oder Remove beginnt und sagt, was sich für dich ändert. Ein Release sammelt diese Zeilen in der Datei `CHANGELOG.md` jedes Pakets.

Der Build dieser Doku liest die sieben Dateien, fügt die Notizen einer Version zusammen und schreibt den Eintrag. Ein neues Release steht also nach dem nächsten Deploy der Doku im Changelog, und dem Changelog kann kein Release fehlen.

Dieselben Notizen stehen in jedem Paket auf npm, in `node_modules/@lupinum/ginko/CHANGELOG.md`, und in den [Releases auf GitHub](https://github.com/lupinum-dev/ginko/releases).
