A bundle is everything a site reads: every brick with its values in one language, as one JSON response. `useGinko`, `useGinkoEntry` and `useGinkoQuery` all read from the bundle of the current request.

You never load a bundle yourself. This page explains what is in it, so that the behaviour of a site makes sense.

## What is in a bundle

- **Every brick of the site.** A single has its values. A collection has its entries, in the order the brick sets, each with an id, its values and, with a `route`, its address.
- **One language.** A site with three languages has three bundles. A page in German reads the German bundle.
- **Values that are ready to show.** The work below is done before the site gets the bundle.

## What is done before the site reads

| Step | Result in the bundle |
| --- | --- |
| Checks | Every value fits its field. A value that the rules of the field refuse never gets in. |
| Defaults | A field without a value has its `default`, when the field sets one. |
| Translation | A text without a translation holds the text of the main language, and the entry lists the field in `fallback`. See [Missing translations]($docs.missing-translations). |
| Dates | An entry outside its dates is not in the bundle. A planned change that is due is in effect. |
| Drafts | A draft is not in the bundle of the live site. |
| Markdown | A Markdown text is a tree, not a string. No parser runs in the browser. |
| Links | A link written as `$news.opening` is the address of that entry in this language. |
| Images | An image has its address, its size and its description. |

So a page shows what it reads. It does not check dates, pick a language or parse Markdown.

## Why one response per language

- **One request per page.** A page with opening hours, a menu and three notices needs one bundle, not five queries. The site loads the bundle once per request, and every composable reads from it.
- **No half pages.** All bricks come from the same moment. A page never shows new hours next to an old notice.
- **One failure to handle.** Either the bundle is there, or the page answers with 503. No part of a page is missing without a sign.
- **Typed.** The bundle follows `ginko.config.ts`, so `menu.items[0].data.price` has a type in your editor.

The cost is size: a bundle holds the whole site, also the bricks a page does not use. The [limits]($docs.limits) of a site keep a bundle small enough for this.

## Where a bundle comes from

| Source of the bricks | Who makes the bundle | When |
| --- | --- | --- |
| Files only | The build | At build time. The dev server makes it again when a file changes. |
| Platform | The platform | The site fetches it when it renders a page. |
| Both | Both | The site joins the two parts. A page does not see the difference. |

A site whose bricks all come from files never asks the platform. Its content changes with a deploy.

## How fresh a bundle is

On a platform site, a host such as Vercel keeps each rendered page for at most 60 seconds. So a published change is on the site within 60 seconds. With a site token, the platform has the changed pages rendered again at once, see [Environment variables]($docs.environment-variables).

"Today" is part of this. A lunch menu for Tuesday shows on Tuesday without a deploy, because the site asks for the content that is in effect now, in the time zone of the site.

## When there is no bundle

If the platform does not answer, the site has no bundle and the page answers with **503**, never with 404. A host such as Vercel then keeps the last good page. [Handle missing content]($docs.missing-content) shows what to build for this case.

Do not read content in `error.vue`: on a 503 there is no bundle, and the error page would fail too.
