Diese Anleitung fügt einer Doku-Seite einen Blog und einen Changelog hinzu. Am Ende listet `/blog` deine Beiträge, `/blog/rss.xml` ist der Feed, `/changelog` listet deine Releases, und die Kopfzeile verlinkt auf beide.

Beide Teile sind optional und hängen nicht voneinander ab.

## Bevor du beginnst

Du brauchst eine Seite mit dem Doku-Kit, siehe [Eine Doku-Seite starten]($docs.start-a-docs-site). Das Template `docs` hat den Changelog schon.

## Den Blog hinzufügen

::steps
#### Die Bausteine und die Listenseite hinzufügen

```ts [ginko.config.ts]
import { blogCollections, blogPages, components, docsCollection, homePages } from '@lupinum/ginko-docs/config'

export default defineSite({
  // …
  pages: {
    home: homePages({ locales }),
    blog: blogPages({ locales }),
  },
  bricks: {
    docs: docsCollection({ locales }),
    ...blogCollections({ locales }),
  },
})
```

`blogCollections` gibt zwei Bausteine zurück, `posts` und `authors`. `blogPages` trägt die Listenseite in `pages` ein, also kennen die Sitemap und ein statischer Build sie.

#### Einen Autor hinzufügen

Ein Autor ist eine YAML-Datei. Ihr Name ist die ID des Autors:

```yaml [content/authors/jane.yml]
name: Jane Doe
role: Maintainer
url: https://example.com/jane
```

`avatar` nimmt ein Bild. Autoren haben keine eigene Seite.

#### Einen Beitrag schreiben

```markdown [content/posts/1.hello.md]
---
title: Version 2 ist da
description: Was in Version 2 neu ist.
date: 2026-11-20
authors: [authors/jane]
tags: [release]
---

Version 2 hat einen neuen Client und typisierte Webhooks.
```

Die Adresse kommt aus dem Dateinamen: Dieser Beitrag liegt unter `/blog/hello`. `image` gibt dem Beitrag und seiner Karte ein Bild.

#### Den Dev-Server neu starten

Stopp den Dev-Server und starte ihn neu. Das Kit fügt die Blog-Seiten beim Start des Servers hinzu.
::

## Den Changelog hinzufügen

::steps
#### Den Baustein und die Seite hinzufügen

```ts [ginko.config.ts]
import { changelogCollection, changelogPages } from '@lupinum/ginko-docs/config'

// …
  pages: { changelog: changelogPages({ locales }) },
  bricks: { changelog: changelogCollection() },
```

#### Eine Datei pro Release schreiben

```markdown [content/changelog/v2-0-0.md]
---
version: 2.0.0
date: 2026-11-20
---

- Der Client hat typisierte Webhooks.
- `createMonitor` nimmt eine Liste `regions`.
```

Schreib den Dateinamen ohne Punkte, denn ein Punkt gilt als Sprache: `v2-0-0.md`, nicht `v2.0.0.md`.
::

## Prüfe, ob es funktioniert

- `/blog` zeigt den Beitrag mit Datum, dem Autor „Jane Doe“ und dem Tag „release“. Der neueste Beitrag steht oben.
- `/blog/hello` zeigt den Beitrag.
- `/blog/rss.xml` ist ein RSS-Feed mit Titel und Beschreibung jedes Beitrags. Andere Sprachen haben ihren eigenen Feed unter `/<language>/blog/rss.xml`.
- `/changelog` zeigt alle Releases, die neuesten zuerst. Jedes hat einen Anker wie `#v2-0-0`.
- Die Kopfzeile hat die Links „Blog“ und „Changelog“.

## Gut zu wissen

- Der Feed enthält Titel und Beschreibung eines Beitrags, nicht seinen Text.
- Ohne `blogPages` oder `changelogPages` in `pages` warnt der Build, und die Listenseite fehlt in der Sitemap.
- Das Kit findet seine Inhalte über die Baustein-Schlüssel `posts`, `authors` und `changelog`. Behalte diese Namen.
- Ein Beitrag oder ein Release in einer anderen Sprache ist eine Datei mit dem Sprachcode: `1.hello.de.md`.
