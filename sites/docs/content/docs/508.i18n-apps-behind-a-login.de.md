---

Diese Anleitung gibt dem Teil einer App hinter einem Login eine eigene Sprachregel. Am Ende erscheint `/app` in der Sprache der Nutzer, die Adresse enthält keine Sprache, und ein Button wechselt die Sprache ohne Neuladen.

Auf öffentlichen Seiten kommt die Sprache aus der Adresse. Hinter einem Login ist das falsch: Dort entscheidet die Einstellung der Nutzer, und `/app/invoices` ist eine Adresse für alle. Eine *Zone mit Nutzersprache (user-locale zone)* ist eine Menge von Pfaden, deren Sprache von den Nutzern kommt. Kurz heißt sie hier Nutzer-Zone.

## Bevor du beginnst

Die App hat `@lupinum/ginko-i18n` eingerichtet, siehe [i18n-Schnellstart]($docs.i18n-quick-start). Die Zone braucht einen Server: Sie kann nicht Teil eines statischen Builds sein.

## Schritte

::steps
#### Die Zone benennen

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@lupinum/ginko-i18n'],
  i18n: {
    locales: ['en-GB', 'de-AT'],
    defaultLocale: 'en',
    baseUrl: 'https://example.com',
    userLocale: ['/app/**'],
  },
})
```

`'/app/**'` ist `/app` und alles darunter. Für eine App, die ganz hinter einem Login liegt, schreib `['/**']`.

#### Eine Seite in der Zone anlegen

```vue [app/pages/app/index.vue]
<script setup lang="ts">
const { t, locale, locales, switchLocale } = useI18n()
</script>

<template>
  <main>
    <h1>{{ t('app.title') }}</h1>
    <button
      v-for="l in locales"
      :key="l.code"
      :disabled="l.code === locale"
      @click="switchLocale(l.code)"
    >
      {{ l.name }}
    </button>
  </main>
</template>
```

```json [i18n/en.json]
{ "app": { "title": "Dashboard" } }
```

```json [i18n/de.json]
{ "app": { "title": "Übersicht" } }
```

Ergänze die zwei Schlüssel in deinen vorhandenen Sprachdateien.

#### Das Cookie beim Login setzen

Der Server liest das Cookie `ginko_locale`. Setz es aus der Einstellung im Konto der Nutzer, dann hat schon die erste Seite nach dem Login die richtige Sprache:

```text
Set-Cookie: ginko_locale=de; Path=/; Max-Age=31536000; SameSite=Lax
```
::

## Prüfe, ob es funktioniert

- Öffne `/app`. Die Seite zeigt „Dashboard“, oder „Übersicht“, wenn dein Browser Deutsch anfragt.
- Drück „Deutsch“. Die Seite zeigt sofort „Übersicht“. Die Adresse bleibt `/app`, und der Browser hat das Cookie `ginko_locale=de`.
- Öffne `/de/app`. Die Antwort ist 404: Die Zone hat kein Präfix.
- Öffne eine öffentliche Seite wie `/about`. Sie ist weiter Englisch. Das Cookie ändert keine Seiten außerhalb der Zone.

## Wie die Zone die Sprache wählt

Der Server legt die Sprache einmal pro Anfrage fest, in dieser Reihenfolge:

1. das Cookie `ginko_locale`,
2. der Header `Accept-Language` des Browsers,
3. die Hauptsprache.

Der Browser übernimmt die Sprache vom Server und erkennt sie nie neu. So stimmen das HTML vom Server und die Seite im Browser überein.

## Was in einer Zone anders ist

- **Keine Head-Tags für Suchmaschinen.** Eine Seite in der Zone hat `lang` und `dir`, aber keinen Canonical-Link, kein `hreflang` und kein `og:locale`. Es gibt keine andere Adresse, auf die sie zeigen könnten. `alternates` ist eine leere Liste.
- **Nicht in der Sitemap, nicht vorgerendert.** Das Modul hält Seiten der Zone aus beidem heraus.
- **`switchLocale` wirkt an Ort und Stelle.** In einer Zone schreibt es das Cookie, lädt die Texte und rendert neu. Auf einer öffentlichen Seite geht es zur selben Seite in der anderen Sprache.
- **Datumsangaben folgen der Region des Browsers.** Mit der Sprache `en` zeigt ein Browser mit `en-GB` 25/10/2026 und einer mit `en-US` 10/25/2026. Eine Sprache mit Region, etwa `de-AT`, behält ihre Region.

::callout{type="warning" title="Seiten der Zone nicht cachen"}
Setz für eine Zone keine Route-Rules `isr`, `swr` oder `cache`. Die Sprache kommt aus einem Cookie, also bekäme jeder Besucher die Sprache des ersten. Der Build warnt, wenn eine Regel das tut.
::

## Zone oder exclude

| Einstellung | Bedeutet | Die Seite erscheint in |
| --- | --- | --- |
| `userLocale` | von den Nutzern lokalisiert | der Sprache der Nutzer |
| `exclude` | nicht lokalisiert | der Hauptsprache |

Pfade in `exclude`, `/api/**` und die internen Pfade von Nuxt liegen nie in einer Zone. So lässt `userLocale: ['/**']` sie in Ruhe.
