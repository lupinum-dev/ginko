The bricks and fields of your config are the schema of the site. The platform keeps its own copy, because the owners' content depends on it. This guide brings a change of the schema to the platform. At the end, the Studio shows the new brick or field, and you know why some changes are refused.

A site whose bricks all come from files has no schema on the platform and needs none of this.

## Before you start

You have the address of the platform and a key with "Publish and back up". [Move a brick to the platform]($docs.move-a-brick-to-the-platform) shows where the key comes from.

The CLI does not read `.env` files. Set the variables in the shell, or as secrets in CI:

```bash
export GINKO_PLATFORM=https://platform.example.com
export GINKO_KEY=ginko_linde_…
```

## Steps

::steps
#### Check before you commit

```bash
npx ginko check
```

The command writes nothing. Without a change it says:

```text
Site “linde”: schema version 1, content 1.
No schema changes.
OK: A release with this schema would be accepted.
```

With a change it lists each one. `+` is an allowed change:

```text
Allowed changes:
  + New brick “promo”.
```

#### Fix what is refused

A change that could break content or older site code is refused. The message says what to do:

```text
✗ promo.until: Field “promo.until” is missing.
  → Add a new field, fill it with a migration and list the old field under `retired`.
    // Keep “until” in bricks.promo.fields as it is in production; retired, it leaves the Studio.
    retired: { 'promo.until': { drop: true } },
```

A schema only grows. You do not delete a field: you retire it. You do not change the type of a field: you add a new field and fill it from the old one. [Schemas only grow]($docs.schemas-only-grow) has every rule.

#### Commit and push

The platform identifies a release by its commit. Commit the change and push it before you release.

A second release of the same commit writes nothing and returns the result of the first. That makes a repeated CI run safe. It also means that a release from uncommitted changes does not arrive when that commit was released before.

#### Release in CI

Run the release on your main branch, before the deploy:

```bash
result=$(npx ginko release)
if [ "$(echo "$result" | jq -r .deploy)" = "true" ]; then
  npx vercel deploy --prod   # or the deploy command of your host
fi
```

A successful release prints one line:

```json
{"ok":true,"deploy":true,"schemaRev":2,"contentRev":2}
```

Deploy only when `deploy` is `true`. When a newer commit is already on the branch, the release steps back:

```json
{"ok":true,"deploy":false,"reason":"superseded"}
```

#### Check the result

Run `npx ginko check` again. It says "No schema changes." Open the Studio: the new brick or field is there.
::

## Release by hand

Outside CI, the release needs the commit. It reads `GITHUB_SHA` in GitHub Actions; by hand you set `GINKO_COMMIT`:

```bash
GINKO_COMMIT=$(git rev-parse HEAD) npx ginko release
```

The commit must be the newest one of `main` on `origin`. For another branch, set `GINKO_BRANCH` too. Without the commit, the command stops with `The environment variable GINKO_COMMIT is missing.`

## A pull request from a fork

GitHub passes no secrets to a pull request from a fork. Run the check without the comparison there:

```bash
npx ginko check --offline
```

It checks the config, the content files and the links, and prints `Skipped the comparison with production (--offline).`
