## Two kinds of site

How you deploy depends on where the content comes from:

- **Files only.** Every brick has `source: 'files'`. The content is fixed at build time. You can build a static site with `nuxt generate` and put it on any static host, or deploy it to Vercel like any Nuxt site.
- **Platform.** At least one brick comes from the platform. Owners change content after the deploy, so the site needs a server that fetches new content. Ginko is made and tested for **Vercel**.

Before the deploy, run `ginko check` in CI. It checks the configuration, the content files and the links, and exits with code 1 on an error. See [Platform and CLI]($docs.plattform-und-cli).

## Vercel

Import the repository on Vercel. Vercel detects Nuxt and runs `nuxt build`; you change nothing in the build settings.

Set `url` in `ginko.config.ts` to the production address. Ginko marks every other host, such as Vercel's preview deployments, with `noindex`, so previews never reach a search engine (see [SEO and agents]($docs.seo-und-agenten)).

The module sets these cache rules for you (Vercel ISR). Your own `routeRules` in `nuxt.config.ts` win: Ginko fills only what you leave unset.

- Every page is cached and rendered again at most every **60 seconds**. Query parameters share one cache entry. The 60 seconds are a default, not a promise: with your own rule for `/**` (for example `routeRules: { '/**': { isr: 300 } }`), Ginko keeps yours. A rule for a narrower path, such as `/news/**`, wins anyway.
- `/api/**` is not cached, because your own server routes may depend on the language of the visitor.
- `/__ginko/**` is never cached. Of these paths, `/__ginko/search/<language>.json` and `/__ginko/docs-mcp` are stable, as are the `.md` addresses, `/llms.txt` and `/llms-full.txt`. Everything else under `/__ginko/` (the preview and the content endpoints) is internal and can change.
- If the platform does not answer, the page answers with **503** and Vercel keeps the last good page.

Ginko also turns off `experimental.payloadExtraction`. With it, Nuxt fetches a `_payload.json` on client navigation, and the server renders the target page with the content of production for it. Pages read the content that is already in the browser instead. So the preview never shows production content, and a navigation costs no extra render.

### A platform site

A site with platform bricks needs these environment variables on Vercel:

| Variable | Value |
| --- | --- |
| `NUXT_PUBLIC_GINKO_PLATFORM` | The address of the platform. Without it, the site has no platform content. |
| `NUXT_GINKO_REVALIDATE_TOKEN` | A random secret of at least 32 characters. Optional, see below. |

Without `NUXT_GINKO_REVALIDATE_TOKEN`, a published change reaches the site within 60 seconds. Ginko gives the token to Vercel as `bypassToken`, unless your `nuxt.config.ts` sets `nitro.vercel.config.bypassToken` itself. With it, the platform renders the changed pages again right after a publish, and owners can use "Update website now". The platform must know the same value: send it to Lupinum, who store it for your site.

In CI, `ginko release` brings a new schema to production before the deploy. A superseded run is not an error: it ends with exit code 0 and prints `"deploy":false`. So deploy only when it prints `"deploy":true`. The page [Platform and CLI]($docs.plattform-und-cli) has a CI snippet and the table of exit codes.

::callout{type="info"}
The platform is hosted by [Lupinum](https://lupinum.com) and open by invitation. A site whose bricks all come from files needs no platform and none of these variables.
::

## Static build (files only)

A site whose bricks all come from files can be built as plain files:

```bash
npx nuxt generate
```

The output in `.output/public` holds every page in every language, the Markdown version of each entry, `/llms.txt`, `/llms-full.txt`, `/sitemap.xml`, `/robots.txt`, the search index and, for a docs site, the RSS feeds. Upload the folder to any static host. A broken link or a page that fails to render stops the build.

A static host has no server. So these parts do not work there:

- **Redirects with patterns.** Exact paths, from `redirectFrom` and from `redirects`, become part of the output. Rules with `:name` or `*` need a server.
- **`Accept: text/markdown`.** The `.md` addresses work; asking the normal address for Markdown needs a server and does not work here.
- **The docs MCP endpoint** (`/__ginko/docs-mcp`).
- **`noindex` on preview hosts.** The static `robots.txt` is written for the production address. Keep preview deployments out of search engines with your host's own setting.

Need any of these? Deploy the same site with `nuxt build` to Vercel instead.

## Docs sites

A site with `@lupinum/ginko-docs` reads its pages from files, so both ways work: `nuxt generate` for a static host, or Vercel for the MCP endpoint and redirects with patterns.

Ginko's own docs also publish the shadcn-vue registry of the components under `/r`. Its build (`pnpm --filter @lupinum/ginko-components registry`) writes the item links from `url` in `sites/docs/ginko.config.ts`. `GINKO_REGISTRY_URL` overrides that address, for example `http://localhost:3500/r` for a local test.
