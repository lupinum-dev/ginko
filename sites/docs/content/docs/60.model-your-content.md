This guide turns a list of "things that change on the site" into the `bricks` of `ginko.config.ts`. At the end, `ginko check` accepts your config, and each brick has a clear owner.

The example is a restaurant with contact details, a menu and news.

## Steps

::steps
#### List what changes, and who changes it

Write down every part of the site that someone will change after launch. Leave out what only a developer touches together with the layout.

| Content | Who changes it | How often |
| --- | --- | --- |
| Address and phone | the owner | once a year |
| Dishes and prices | the owner | every week |
| News | the developer, for now | every month |

#### Decide: one thing or many

A **single** holds exactly one entry. A **collection** holds many entries with the same fields.

| The content is | Use | Example |
| --- | --- | --- |
| one set of values for the whole site | `single` | contact details, opening hours, the start page |
| a list that grows and shrinks | `collection` | dishes, news, events, team members |

Rows inside one entry, such as the days of one lunch menu, are a list field (`f.list`), not a collection.

#### Name the fields

Give each brick the values it needs, and no more. Each field has a type. [Field types]($docs.field-types) lists all of them.

```ts [ginko.config.ts]
import { collection, defineSite, f, single } from '@lupinum/ginko'

export default defineSite({
  // site, name, url, timeZone, locales, currency, pages
  bricks: {
    contact: single({
      label: 'Address and contact',
      fields: {
        street: f.text('Street and number', { max: 80, translate: false }),
        phone: f.text('Phone', { format: 'tel' }),
      },
    }),
    menu: collection({
      label: 'Menu',
      fields: {
        name: f.text('Name', { max: 120 }),
        price: f.money('Price'),
      },
      max: 150,
      order: 'manual',
    }),
  },
})
```

The key (`contact`, `menu`) is the name of the brick. It starts with a lowercase letter and has only letters and digits.

#### Set the size and order of each collection

A collection needs two more settings:

- `max` is the largest number of entries, from 1 to 500.
- `order` is the order in which the site reads them. `'manual'` keeps the order the owner sets. `{ field: 'date', dir: 'desc' }` sorts by a field, here newest first.

#### Decide where each brick lives

A brick without `source` lives on the platform, and the owner changes it in the Studio. A brick with `source: 'files'` lives in files in the repository, and a developer changes it.

```ts
news: collection({
  label: 'News',
  source: 'files',
  // …
}),
```

Use the table from step 1: what the owner changes goes to the platform, what the developer changes goes to files. A brick can move later, and the pages that read it stay the same. [Write content in files]($docs.write-content-in-files) shows the files.

#### Check the config

```bash
npx ginko check
```

The command prints `OK: schema and links are fine.` or names each problem with its brick and field.
::

## Make a long form easier to fill

A brick with many fields gives the owner a long form. Give fields a `group`, and the Studio shows each group under its heading. With `layout: 'tabs'` the groups become tabs on wide screens.

```ts
legal: single({
  label: 'Legal',
  layout: 'tabs',
  fields: {
    imprint: f.markdown('Imprint', { group: 'Imprint' }),
    privacy: f.markdown('Privacy', { group: 'Privacy' }),
  },
}),
```

Groups change the form only. The data stays the same.

## Limits

One site has at most 30 bricks. One brick has at most 60 fields.
