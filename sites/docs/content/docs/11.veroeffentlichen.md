## Zwei Arten von Seiten

Wie du veröffentlichst, hängt davon ab, woher die Inhalte kommen:

- **Nur Dateien.** Jeder Baustein hat `source: 'files'`. Die Inhalte stehen beim Build fest. Du kannst mit `nuxt generate` eine statische Seite bauen und auf jeden statischen Host legen, oder sie wie jede Nuxt-Seite auf Vercel bringen.
- **Plattform.** Mindestens ein Baustein kommt von der Plattform. Inhaber ändern Inhalte nach dem Deploy, also braucht die Seite einen Server, der neue Inhalte holt. Ginko ist für **Vercel** gemacht und dort getestet.

Lass vor dem Deploy `ginko check` in der CI laufen. Es prüft die Konfiguration, die Inhaltsdateien und die Links und endet bei einem Fehler mit Code 1. Siehe [Plattform und CLI]($docs.plattform-und-cli).

## Vercel

Importiere das Repository auf Vercel. Vercel erkennt Nuxt und führt `nuxt build` aus; an den Build-Einstellungen änderst du nichts.

Setz `url` in `ginko.config.ts` auf die Adresse der Produktion. Ginko markiert jeden anderen Host, etwa die Vorschau-Deployments von Vercel, mit `noindex`, damit Vorschauen nie in einer Suchmaschine landen (siehe [SEO und Agenten]($docs.seo-und-agenten)).

Das Modul setzt diese Cache-Regeln für dich (Vercel ISR):

- Jede Seite wird zwischengespeichert und höchstens alle **60 Sekunden** neu gerendert. Query-Parameter teilen sich einen Cache-Eintrag.
- `/api/**` wird nicht zwischengespeichert, weil deine eigenen Server-Routen von der Sprache des Besuchers abhängen können.
- `/__ginko/**` (die Vorschau und die Inhalts-Endpunkte) wird nie zwischengespeichert.
- Antwortet die Plattform nicht, antwortet die Seite mit **503**, und Vercel behält die letzte gute Seite.

### Eine Plattform-Seite

Eine Seite mit Plattform-Bausteinen braucht diese Umgebungsvariablen auf Vercel:

| Variable | Wert |
| --- | --- |
| `NUXT_PUBLIC_GINKO_PLATFORM` | Die Adresse der Plattform. Ohne sie hat die Seite keine Inhalte von der Plattform. |
| `NUXT_GINKO_REVALIDATE_TOKEN` | Ein zufälliges Geheimnis mit mindestens 32 Zeichen. Optional, siehe unten. |

Ohne `NUXT_GINKO_REVALIDATE_TOKEN` erreicht eine veröffentlichte Änderung die Seite innerhalb von 60 Sekunden. Mit ihm rendert die Plattform die geänderten Seiten gleich nach dem Veröffentlichen neu, und Inhaber können „Website jetzt aktualisieren“ nutzen. Die Plattform muss denselben Wert kennen: Schick ihn an Lupinum, dort wird er für deine Seite hinterlegt.

In der CI bringt `ginko release` ein neues Schema vor dem Deploy in die Produktion. Veröffentliche nur, wenn es `"deploy":true` ausgibt. Die Seite [Plattform und CLI]($docs.plattform-und-cli) hat die Details.

::callout{type="info"}
Die Plattform wird von [Lupinum](https://lupinum.com) betrieben und ist auf Einladung offen. Eine Seite, deren Bausteine alle aus Dateien kommen, braucht keine Plattform und keine dieser Variablen.
::

## Statischer Build (nur Dateien)

Eine Seite, deren Bausteine alle aus Dateien kommen, lässt sich als reine Dateien bauen:

```bash
npx nuxt generate
```

Die Ausgabe in `.output/public` enthält jede Seite in jeder Sprache, die Markdown-Fassung jedes Eintrags, `/llms.txt`, `/llms-full.txt`, `/sitemap.xml`, `/robots.txt`, den Suchindex und, bei einer Doku-Seite, die RSS-Feeds. Lade den Ordner auf einen beliebigen statischen Host. Ein kaputter Link oder eine Seite, die nicht rendert, stoppt den Build.

Ein statischer Host hat keinen Server. Darum geht dort Folgendes nicht:

- **Weiterleitungen mit Mustern.** Genaue Pfade, aus `redirectFrom` und aus `redirects`, landen in der Ausgabe. Regeln mit `:name` oder `*` brauchen einen Server.
- **`Accept: text/markdown`.** Die `.md`-Adressen gehen; die normale Adresse nach Markdown zu fragen geht nicht.
- **Der MCP-Zugang der Doku** (`/__ginko/docs-mcp`).
- **`noindex` auf Vorschau-Hosts.** Die statische `robots.txt` ist für die Adresse der Produktion geschrieben. Halte Vorschau-Deployments mit der Einstellung deines Hosts aus Suchmaschinen heraus.

Brauchst du etwas davon? Dann bring dieselbe Seite mit `nuxt build` auf Vercel.

## Doku-Seiten

Eine Seite mit `@lupinum/ginko-docs` liest ihre Seiten aus Dateien, also gehen beide Wege: `nuxt generate` für einen statischen Host, oder Vercel für den MCP-Zugang und Weiterleitungen mit Mustern.

Die Ginko-Doku selbst veröffentlicht außerdem die shadcn-vue-Registry der Komponenten unter `/r`. Ihr Build (`pnpm --filter @lupinum/ginko-components registry`) schreibt die Links der Einträge aus `url` in `sites/docs/ginko.config.ts`. `GINKO_REGISTRY_URL` überschreibt diese Adresse, zum Beispiel `http://localhost:3500/r` für einen Test auf dem eigenen Rechner.
