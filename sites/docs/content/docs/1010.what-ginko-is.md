Ginko connects a Nuxt site with its content. You build the site with normal Nuxt code. The content lives outside that code, so the people who own the site can change it without a developer.

## Where the content lives

A site has two possible sources for its content:

- **Files.** Texts are Markdown and data files in the repository, next to the code. Developers change them. Examples: these docs, a blog, legal pages.
- **Platform.** Owners and staff change the content in a web app, the Studio, which Lupinum hosts and opens by invitation. Examples: opening hours, a menu, events.

A site can use both at once. The pages read both the same way, so a text can start as a file and move to the platform later. The code of the page does not change.

## The four words

- A **brick** is one kind of content, for example "Menu". You describe it in `ginko.config.ts`.
- A **field** is one value in a brick, for example a name or a price.
- An **entry** is one record of a brick, for example one dish.
- A **bundle** is everything the site reads: all bricks with their values in one language, as one JSON response.

```ts [ginko.config.ts]
bricks: {
  menu: collection({                      // a brick
    label: 'Menu',
    fields: {
      name: f.text('Name'),               // a field
      price: f.money('Price'),
    },
    max: 150,
    order: 'manual',
  }),
}
```

From this description Ginko makes the form in the Studio, the checks on every value, the types in your code and the bundle.

## When Ginko fits

Use Ginko when a site has content that changes often, and the person who changes it should not touch code. Opening hours, a lunch menu, events and job ads are typical.

Use it with files alone when developers keep all texts and you want typed content, translations and search without a platform.

## When it does not fit

- **You want a page builder.** In Ginko you define the bricks and their fields. The layout stays code in your Nuxt site.
- **The content never changes.** A site with fixed texts does not need Ginko.
