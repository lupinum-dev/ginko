## Single and collection

A brick describes one type of content. There are two kinds:

- `single` is a **single**: exactly one entry. Examples: opening hours, imprint, contact details.
- `collection` is a **collection**: many entries with the same fields. Examples: dishes, events, notices.

Both go under `bricks` in `defineSite`. The key is the name of the brick. It starts with a lowercase letter and contains only letters and digits, for example `menu`.

```ts
import { collection, defineSite, f, single } from '@lupinum/ginko'

export default defineSite({
  site: 'restaurant',
  name: 'Gasthaus zur Linde',
  url: 'https://ginko-demo-restaurant.vercel.app',
  timezone: 'Europe/Vienna',
  locales: ['de', 'en'],
  currency: 'EUR',
  pages: { home: { de: '/', en: '/en' }, menu: { de: '/speisekarte', en: '/en/menu' } },
  bricks: {
    contact: single({
      label: 'Address and contact',
      fields: {
        street: f.text('Street and number', { max: 80, translate: false }),
        phone: f.text('Phone', { format: 'tel' }),
      },
    }),
    menu: collection({
      label: 'Menu',
      fields: {
        name: f.text('Name', { max: 120 }),
        price: f.money('Price'),
      },
      max: 150,
      order: 'manual',
    }),
  },
})
```

Both functions take these settings:

| Setting | Applies to | Meaning |
| --- | --- | --- |
| `label` | both | Name of the brick in the editor. Required. |
| `describe` | both | Short explanation in the editor, a text or a text per language like `label`. Bricks and components say what they are for with `describe`; a field has `hint` for the help text under it. |
| `fields` | both | The fields of the brick. Required. |
| `source` | both | `'files'` reads the brick from Markdown files. Without it, the brick comes from the platform. |
| `tasks` | both | Tasks for the editor. See below. |
| `max` | collection | Largest number of entries, 1 to 500. Required. |
| `order` | collection | Order of the entries. Required. |
| `route` | collection | Address of the detail pages, per locale. |
| `visible` | collection | When an entry is visible. |
| `untranslated` | collection | What happens when a translation is missing. |
| `plans` | collection | Entries plan weeks of a single brick ahead. |

Limits of one site: at most 30 bricks, and at most 60 fields per brick.

## Field types

You build fields with `f.<type>('Label', settings)`. The label is the name in the editor. The settings are an object.

These settings work for every type:

- `optional: true` makes the field optional. Without it, a field is required.
- `hint` is a help text in the editor. Like the label, it is a text or a text per language: `{ de: '…', en: '…' }`.
- `showWhen` shows the field in the editor only while another field next to it has a value: `{ field: 'closed', is: true }` or `{ field: 'closed', not: true }`. A missing value counts as "not". The stored value and the checks stay; only the editor hides the field.
- `default` is the start value, written like the field's value: a text, a number, `{ amount: 1250 }` for money, an option value for a choice. For a translatable field, a plain text is the text of the main language, and `{ de: 'Hallo', en: 'Hello' }` sets one text per language; Ginko keeps only the site's locales. If no text in the main language is left, the default is left out (for example, a preset written for other languages). `f.markdown`, `f.image` and `f.file` have no default.
- `translate: false` turns translation off for a field. `translate: 'manual'` allows no automatic translation suggestions.

The column "Bundle value" shows what `useGinko` returns in the site.

| Field | Settings | Bundle value | Translatable |
| --- | --- | --- | --- |
| `f.text` | `max` (up to 500, or 2000 with `format: 'url'`, default 200), `format`: `'url'`, `'email'`, or `'tel'` | string | yes, no with `format` |
| `f.longtext` | `max` (up to 5000, default 2000) | string | yes |
| `f.markdown` | `profile`: `'inline'`, `'basic'`, `'rich'` or `'page'`, `max` (default 50000). No `default` | Markdown tree | yes |
| `f.number` | `min`, `max`, `step` (all three required), `unit` | number | no |
| `f.money` | `min`, `max` (in minor units, e.g. cents; no negative amounts), `currency` | `{ amount, currency }` | no |
| `f.boolean` | none | `true` or `false` | no |
| `f.date` | none | `'2026-10-10'` | no |
| `f.time` | none | `'18:30'` | no |
| `f.daterange` | none | `{ from, to }`, both as dates | no |
| `f.choice` | `options` (list of options, up to 50) | the value of the option | no |
| `f.choices` | `options`, `max` | list of values | no |
| `f.list` | `itemLabel`, `fields`, `max` (1 to 50, required), `min`, `unique` | list of rows, each with `_id` | per column |
| `f.image` | none | `{ url, alt, width, height, focus? }` | only `alt` |
| `f.file` | `accept: ['pdf']`, `maxBytes` (up to 10 MB, 10 * 1024 * 1024) | `{ url, name, size }` | no |
| `f.slug` | `from` (required) | string | yes |
| `f.ref` | `to`: a collection brick (required) | the ID of one entry | no |
| `f.refs` | `to` (required), `max` | list of entry IDs | no |

Notes on single types:

- **Markdown profiles** set what a text may contain. `inline`: one paragraph with bold, italic, strikethrough, code and links. `basic`: also headings h2–h4, lists and task lists (`- [ ] item`), quotes, dividers and footnotes. `rich`: also tables, images, code blocks, math and mermaid diagrams. `page`: also h1, h5, h6 and components (`::callout`). Raw HTML always stays text.
- **Money** is stored in minor units, e.g. whole cents (a currency without them, such as JPY, uses whole units). The amount 12.50 EUR is `{ amount: 1250, currency: 'EUR' }`. Amounts cannot be negative. Without `currency`, the field uses the currency of the site. Use `formatMoney` to show the value.
- **Date and time** are strings. A date is `YYYY-MM-DD`, a time is `HH:MM`. A date counts in the time zone of the site.
- **Choices:** `f.choice` and `f.choices` take the options as `options` in the second argument, for example `f.choice(label, { options: ['a', 'b'], default: 'a' })`. An option is a string or `{ value, label }`. The bundle holds only the value. The label is editor text: one text, or one per locale like every `Label`. It is not in the bundle, so show your own texts per locale in the site.
- **Lists:** `f.list(label, { itemLabel, fields: columns, ...settings })`. `itemLabel` names one row, for example "Day". `min` is the smallest number of rows. `unique` names a required column whose value must differ in every row. A list cannot contain a list.
- **Images and files** are uploaded in the editor on the platform. The bundle holds the URL. For images, Ginko also makes WebP copies 480, 960 and 1600 px wide (only those smaller than the image), at upload on the platform and at build for files. `<GinkoImage>` offers them to the browser with `srcset`, so phones load small files.
- **Image description (`alt`)** is required in the main language. A field can have its own text; without one, the description from the Files library applies. The bundle holds the result. When the owner set a focus point, the image value also has `focus: { x, y }` (0 to 1), and `<GinkoImage>` keeps that point in the crop.
- **Slug** is the address of an entry. See below.
- **Platform-managed properties.** The stored types `Field` and `Brick` also have `pos` and `retired`. The platform sets them; `f.*`, `single` and `collection` do not take them. To retire a field, use `retired` in the site config (see [Platform and CLI]($docs.plattform-und-cli)).

An example with a list and a choice:

```ts
const weekdays = [
  { value: 'mo', label: 'Monday' },
  { value: 'tu', label: 'Tuesday' },
  { value: 'we', label: 'Wednesday' },
] as const

const lunch = single({
  label: 'Lunch menu',
  fields: {
    weekOf: f.date('Week of'),
    days: f.list('Days', {
      itemLabel: 'Day',
      fields: {
        day: f.choice('Day', { options: weekdays }),
        dish: f.text('Dish', { max: 200 }),
        price: f.money('Price', { optional: true }),
      },
      min: 3, max: 3, unique: 'day',
    }),
  },
})
```

In the site, the field `day` has the type `'mo' | 'tu' | 'we' | UnknownChoice`. `UnknownChoice` stands for a value that a later release adds. Handle it with a fallback text.

## Groups and tabs

A long form is easier to fill in parts. Give fields a `group`; the Studio shows each group under its heading. With `layout: 'tabs'` on the brick, the groups become tabs on wide screens. Phones always show headings. Fields without a group come first. Groups only change the form: the data stays the same.

```ts
legal: single({
  label: 'Legal',
  layout: 'tabs',
  fields: {
    imprint: f.markdown('Imprint', { group: 'Imprint' }),
    privacy: f.markdown('Privacy', { group: 'Privacy' }),
  },
}),
```

After a refused save, a tab with an error shows a red dot and opens first.

## Routes and slugs

A collection gets detail pages when it has a `route`. The route names one path per locale, with `[slug]`:

```ts
events: collection({
  label: 'Events',
  fields: {
    title: f.text('Title', { max: 120 }),
    slug: f.slug('Address', { from: 'title' }),
    when: f.daterange('When'),
  },
  max: 30,
  order: { field: 'when', dir: 'asc' },
  route: { de: '/veranstaltungen/[slug]', en: '/en/events/[slug]' },
})
```

These rules apply to a route:

- You must give a path for every locale in `locales`. Each path starts with `/` and contains `[slug]`.
- The path already includes the locale prefix, for example `/en/events/[slug]`.
- The brick needs an `f.slug` field. Its option `from` names the text field that the slug comes from.
- Only collections have slugs. A single with a slug field is an error.

The slug is made once, when an entry is created. Ginko writes ä, ö, ü, and ß as ae, oe, ue, and ss, uses lowercase letters, and joins words with `-`. A duplicate slug gets `-2`, `-3`, and so on. After that, the slug stays fixed. Each locale has its own slug. For file bricks, the slug comes from the frontmatter or the file name (see "Content from files").

You write the page for the route yourself. The page "Reading content" shows how it reads the entry. The page "Languages" shows how the paths fit together per locale.

## Visibility

Use `visible` to show and hide entries by date:

- `{ mode: 'always' }` shows everything. This is the default.
- `{ mode: 'until', field: 'until' }` shows an entry until the date in the field `until` has passed. The field is a `date` or a `daterange`; for a `daterange` the end date (`to`) counts. An empty field always shows the entry. With `days: 6` it stays six days longer, for example a week from its first day.

A date counts for the whole day, in the time zone of the site. `useGinko` filters by this rule. The detail page of an entry that is not visible returns 404. This entry is also missing from the sitemap.

With `deleteExpired: true` in `visible`, the platform deletes entries that are not visible when a new entry needs room. A daily job also deletes entries that have been invisible for 30 days. Deleted entries can be restored for 30 days.

With `plans: { brick: 'lunch', field: 'weekOf' }`, the entries of a collection plan weeks of the single brick `lunch` ahead: `weekOf` (a `date` field of the collection) holds the first day of the week, and a planned week counts as entered for the weekly reminder.

## Order

`order` sets the order of the entries in the bundle:

- `'manual'`: owners arrange the entries by hand on the platform. For files, the number in the file name sets the order.
- `{ field: 'when', dir: 'asc' }` sorts by a field, ascending (`'asc'`) or descending (`'desc'`). A `daterange` field sorts by `from`, then by `to`.

## Tasks

Tasks (`tasks`) are shortcuts in the editor for a frequent chore. A task does not change what is in the data. It sets which fields a staff member sees and may change.

```ts
tasks: [
  { id: 'closedToday', label: 'Closed today', kind: 'edit', fields: ['closedOn', 'closedNote'], prefill: { closedOn: '@today' } },
  { id: 'add', label: 'Add a dish', kind: 'create' },
  { id: 'remove', label: 'Remove a dish', kind: 'remove' },
]
```

- `kind: 'edit'` changes the fields in `fields`. With `pick: true`, the person first picks an entry.
- `kind: 'create'` adds a new entry.
- `kind: 'remove'` deletes an entry.
- `prefill` fills fields of the brick in the form in advance. The platform resolves the tokens `'@today'`, `'@workWeek'`, and `'@nextWorkWeek'` in the time zone of the site. A token needs a `date` field; any other value is written and checked like that field's `default`. `'@workWeek'` is the first day of the work week, `'@nextWorkWeek'` the first day of the week after it. The first day of the week comes from the main language of the site (`languages`, for example Monday for `de-AT`, Sunday for `en-US`) and you can override it with `firstDayOfWeek` (1 to 7, 1 = Monday) in the site config. At the weekend (the days after the last workday) the work week is already the coming week, so a weekly plan made on Saturday is for the week ahead.

Staff members (role `staff`) may only do what matches a task that the owner has granted to them. You can change tasks at any time. They are not part of the data contract.

::callout{type="note"}
Tasks only make sense for platform bricks. The platform never sees bricks with `source: 'files'`, because nobody edits them in the editor.
::
